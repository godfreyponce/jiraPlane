**Goal:** With two displays, a click on either menu bar's copy of the tray icon opens the panel
under that copy, every time. One display and `OPEN_POPOVER=1` behave as today.

**Architecture:** `main.js` only. The two tray handlers pass `screen.getCursorScreenPoint()`
into `togglePopover(trayBounds, cursor)`. When the cursor's display is the display the tray
bounds sit on, nothing changes: the #38 lines run on `trayBounds` as today. When they differ,
the panel is placed on the cursor's display from two facts about that display: the icon sits
the same distance from the right edge on every menu bar (owner's log: 607 px on the external,
605 px on the built-in), and the menu bar's bottom edge is `display.workArea.y`. The `popover:`
log line gains `cursor=x,y` so the choice can be read from the log. `OPEN_POPOVER=1` passes no
cursor and keeps the old path.

**Tech Stack:** electron 43.2.0 (`screen.getCursorScreenPoint`, `screen.getDisplayNearestPoint`,
`screen.getDisplayMatching`), osascript JXA with CoreGraphics for synthetic clicks and the
window probe (proof only, nothing ships).

## Why the bounds are wrong (read from Electron's source during planning)

`shell/browser/ui/tray_icon_cocoa.mm` at v43.2.0, fetched 2026-10-17:

- Left click (`handleClickNotifications`): `NotifyClicked(ScreenRectFromNSRect(event.window.frame),
  ScreenPointFromNSPoint([event locationInWindow]), …)`. The bounds are **the status item's
  window frame**. The third `position` argument is `locationInWindow` run through a screen
  conversion, so its x is 0–32 (inside the icon) and its y is nonsense; it is not the cursor.
- Right click (`rightMouseUp`): `NotifyRightClicked(ScreenRectFromNSRect(event.window.frame), …)`.
  No position at all.

So both handlers get the frame of one NSWindow, the status item's. macOS shows a copy of the
status item on every menu bar but keeps that window on the active menu bar (the display the
owner last worked on); a click on the other display's copy still arrives through that window,
so the frame names the wrong display. This matches the owner's four log lines: the first click
came while the external bar was active (`tray=3433,-269`), the three later ones while the
built-in bar was active (`tray=875,0`). The ticket's "best guess" is confirmed as far as the
Electron side goes; the macOS side (one window, mirrored copies) is still inferred from the
log, not from Apple's code. The fix does not depend on which it is: the cursor is on the
clicked copy either way.

**The flash (Done-when 6):** hypothesis, not reproduced in planning (planning sessions do not
launch the app). Clicking a status item on the inactive menu bar activates that bar for the
click (it brightens from the dimmed inactive look and the item highlights); then our panel shows
on the other display, the active bar flips back, and the external bar dims again. That brighten
and dim is the flash. If the hypothesis holds, the fix removes it: the panel now opens on the
bar that was just activated, so it stays active. If the flash is still there after the fix, it
is the item's own click highlight and cosmetic. Gate 2 item for the owner's eyes; Step 9 says
what the build itself saw on the external screenshot.

## Decisions the owner may want to overturn

1. **Branch, not rewrite: the old path stays for the same-display case.** The transposed
   geometry (right-edge offset, `workArea.y`) is used only when the cursor's display differs
   from the bounds' display. Always computing from the cursor's display would be fewer
   branches but could move the one-display panel by a pixel or two (the status item window's
   height, 33 px on the built-in, is not provably the menu bar height). Done-when 3 says
   "where it does today", so the old lines stay.
2. **The icon's x on the other display comes from the right-edge offset, not from the cursor.**
   The cursor is somewhere inside the 32 px icon, so "left edge = cursor.x" would be off by up
   to 32 px. The right-edge offset was off by 2 px between the owner's two bars (607 vs 605).
   If the build's external screenshot shows the panel visibly off the icon, the fallback is
   `x = cursor.x - 16` (icon centre), reported at gate 2 rather than silently swapped in.
3. **The icon's bottom on the other display is `display.workArea.y`.** That is the menu bar's
   bottom edge (the Dock is never at the top), and the ticket's own wording of the rule is
   "top edge `POPOVER_GAP` below the menu bar". The alternative, reusing the reported icon's
   height on the other display, is wrong by 3 px between the owner's bars (30 vs 33).
4. **`screen.getCursorScreenPoint()` is read in the handler, not Electron's `position`.** Settled
   by the source above: `position` is window-relative and absent on right click.
5. **The log line keeps naming the display the panel was placed on, plus `cursor=`.** Done-when 5
   is met by placing on that display and proving it with the window probe at the same moment.
   A read-back of `popoverWin.getBounds()` after `show()` would be synchronous and would not
   catch a later move; the probe (Step 7) does.

```js
// macOS keeps the status item's window on the active menu bar and Electron
// reports that window's frame as the click bounds, so a click on the other
// display's copy of the icon arrives with the wrong display's bounds (#47).
// The cursor names the clicked display; there, the icon sits the same
// distance from the right edge, and the menu bar ends at workArea.y.
function iconOnClickedDisplay(trayBounds, cursor) {
  const reported = screen.getDisplayMatching(trayBounds);
  const clicked = screen.getDisplayNearestPoint(cursor);
  if (clicked.id === reported.id) return { display: reported, icon: trayBounds };
  const fromRight = reported.bounds.x + reported.bounds.width - (trayBounds.x + trayBounds.width);
  return {
    display: clicked,
    icon: {
      x: clicked.bounds.x + clicked.bounds.width - fromRight - trayBounds.width,
      y: clicked.bounds.y,
      width: trayBounds.width,
      height: clicked.workArea.y - clicked.bounds.y,
    },
  };
}

// cursor is null from the OPEN_POPOVER hook, which has no click.
function togglePopover(trayBounds, cursor = null) {
  if (popoverWin.isVisible()) return popoverWin.hide();
  const { display, icon } = cursor
    ? iconOnClickedDisplay(trayBounds, cursor)
    : { display: screen.getDisplayMatching(trayBounds), icon: trayBounds };
  const { workArea } = display;
  // Left edge under the icon's left edge (NSMenu-style), pulled left if the
  // panel would run off the display.
  const x = Math.round(Math.min(icon.x, workArea.x + workArea.width - POPOVER_SIZE.width));
  const y = Math.round(icon.y + icon.height + POPOVER_GAP);
  popoverWin.setPosition(x, y);
  // #22 habit: a panel in the wrong place can be explained from the log.
  console.log(`${new Date().toISOString()} popover: tray=${trayBounds.x},${trayBounds.y} ` +
    `${trayBounds.width}x${trayBounds.height} cursor=${cursor ? `${cursor.x},${cursor.y}` : '-'} ` +
    `at=${x},${y} display=${describeDisplay(display)}`);
  … (pushPopoverState, show, setAlwaysOnTop unchanged)
}
```
