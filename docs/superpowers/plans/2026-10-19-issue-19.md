# Login LaunchAgent keeps its console output — Implementation Plan (jiraPlane #19)

> gate 2.** Stop there.

**Goal:** The plist that `scripts/install-login-launch.sh` writes sends the login instance's
stdout and stderr to one file outside the repo, so the always-on instance has a log.

**Architecture:** Two keys are added to the installer's plist heredoc: `StandardOutPath` and
`StandardErrorPath`, both set to `$HOME/Library/Logs/jiraplane.log`. The heredoc is unquoted,
so `$HOME` expands at install time (launchd does not expand `~`). `~/Library/Logs` exists on
every Mac, so no `mkdir` is needed. launchd opens the file in append mode and never rotates it;
log growth is handled by a measured note, not by rotation (see Decisions). The `--write-only`
path (#29, the Settings toggle) writes the same heredoc, so it gets the keys with no extra code.
The bootout/bootstrap lines stay as they are; they already upgrade an existing agent in place.

**Tech Stack:** POSIX `sh` (`set -e`), launchd plist, electron 43.2.0.

**Spec:** issue #19 body (no design spec; no comments on the issue).

## Global Constraints

- No new dependency.
- Log outside the repo: console output can carry Jira issue keys and comment snippets.
- Don't add new logging. Don't change what the app logs to console. No `.js` file changes.
- `--write-only` behaviour (#29) unchanged: the plist is written, launchctl untouched.
- **Never run the installer against the real `$HOME` from this worktree** (#53 rule). The plist
  embeds `$REPO`; a full run would point the owner's login job at the worktree. Every installer
  run in the build sets `HOME` to a temp dir and passes `--write-only`.
- T3 gotcha: `npm start` is prefixed `env -u ELECTRON_RUN_AS_NODE` and `TEAMS_WEBHOOK_URL=`.
- One running app instance at a time; quit what you start. Subagents never launch the app.
- Never print or quote `.env` values or `state.json` contents; counts only.

## Decisions the owner may want to overturn

1. **Path and shape: one file, `~/Library/Logs/jiraplane.log`, for both streams.** One file keeps
   stdout and stderr lines in the order they happened (a `teams sink failed` line next to the
   flight it belongs to). `~/Library/Logs` is the macOS place for user logs; Console.app lists it
   and it always exists, so the installer needs no `mkdir`. Alternatives: a
   `~/Library/Logs/jiraPlane/` folder (needs `mkdir -p`), or two files (`.out.log`/`.err.log`).
2. **Growth: a measured note, no rotation.** Planning found that a normal poll cycle with no
   events logs nothing (`main.js` tick: `console.*` only on events and on `poll cycle failed`;
   `poller.js:252/273/314/328` only on seed, skip, flood valve, events). Lines come from flights,
   popover opens, the daily update check, and errors. The worst steady case is Jira unreachable
   or the PAT expired: one `poll cycle failed: …` line per cycle, 1440 cycles a day
   (`POLL_SECONDS` default 60). The build measures the real byte sizes (Step 6) and the note
   states bytes per day for normal operation and for the all-day-failure case. Rotation would
   need a size cap, and the ticket says not to guess one. If the owner wants a real 24-hour
   `wc -c` instead of a per-line measurement times counts, that check runs after landing
   (Landing step 3) and replaces the number in the docs.
3. **The live check of Done-when 2 and 3 runs after the code lands on main, not at gate 2.**
   Running the worktree's installer for real would point the login job at the worktree, which has
   no `.env` (polling disabled) and is deleted later. So the build proves the plist shape with a
   temp `HOME`, and the live proof is the first step of landing: run main's installer over the
   owner's existing agent (that is the "upgrade in place" case itself), then fly a Test flight
   from the panel and read the log. If it fails, the issue stays open and the fix goes forward.

   exposure; not handled. Step 4's `plutil -lint` covers the normal case.
4. **Jira unreachable all day.** Expected: the log grows by the measured failure-line size × 1440
   per day, and the note says so. Pinned by Step 6.
5. **Chromium's own stderr noise** (lines Electron prints that were thrown away before). Expected:
   it lands in the log too, and it counts in the measurement. Pinned by Step 7, which captures
   everything the process writes over three poll cycles.
