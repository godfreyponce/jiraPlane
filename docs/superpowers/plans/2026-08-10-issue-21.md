# Issue #21 — Gate flight start on overlay placement (Implementation Plan)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A flight's animation never starts while any overlay is still on the wrong display — the start waits on every overlay's AeroSpace release settling, instead of the fixed 700ms lead that races it.

**Architecture:** Two-phase start on multi-display setups. `createFlight` stops baking `start` into the query string when more than one physical display is attached; instead, `releaseFromTilingWM` gains a completion callback (fired exactly once on every terminal path: success, ENOENT, retries exhausted, window destroyed), and when all overlays have settled — or a backstop deadline derived from the retry schedule fires — main computes `start = max(createdAt + START_LEAD_MS, now)` and delivers it to every overlay over a new `flight-start` IPC channel. The renderer holds the sim at `s = 0` (fully offscreen — the entry margin is ~194px ≈ 1.1s of flight) until the start arrives. Single-physical-display setups keep today's query-string path byte-for-byte.

**Tech Stack:** Electron (main + sandboxed preload + `plane.html` renderer), AeroSpace CLI. No test suite — verify = run the app (owner rule 2026-08-03).

**Interfaces:**

- Produces: `releaseFromTilingWM(win, isPrimary, attempt = 0, onSettled = () => {})` — `onSettled()` fires **exactly once per top-level call**, on whichever terminal path the release takes: early return (AeroSpace already known missing, or window destroyed), CLI success, ENOENT, or retries exhausted. - [ ] **Step 1: Thread the completion callback through every exit**

Replace the function body (lines 98–112) with:

```js
function releaseFromTilingWM(win, isPrimary, attempt = 0, onSettled = () => {}) {
  if (aerospaceMissing || win.isDestroyed()) return onSettled();
  const windowId = win.getMediaSourceId().split(':')[1];
  const target = isPrimary ? 'main' : 'secondary';
  execFile(AEROSPACE_BIN, ['move-node-to-monitor', '--window-id', windowId, target], (err) => {
    if (!err) {
      // AeroSpace just re-homed the window node; make sure the level survived (#12).
      if (!win.isDestroyed()) win.setAlwaysOnTop(true, 'screen-saver');
      return onSettled();
    }
    if (err.code === 'ENOENT') { aerospaceMissing = true; return onSettled(); }
    // Usually means AeroSpace hasn't detected the window yet — retry briefly.
    if (attempt < 5) return setTimeout(() => releaseFromTilingWM(win, isPrimary, attempt + 1, onSettled), 300);
    onSettled(); // retries exhausted (#21): report so the gate can degrade, don't hang it
  });
}
```

## Decisions of record (and their basis)

1. **Settled = the release's terminal outcome, not a bounds check at `ready-to-show`.** AeroSpace snaps a window only after it becomes visible, so a bounds check at show time can pass *before* the yank — the CLI success is the only signal that the yank-and-restore cycle finished. The Done-when's "confirmed on its intended display" is evidenced by the instrumented run (Task 4 Step 2), not by a product-code bounds assertion.
2. **`start = max(createdAt + 700, all-settled)`** — the 700ms page-load lead stays as a floor (its receipt is unchanged), so every setup that settles fast keeps today's exact start time; only genuinely slow releases push it.
3. **Gate scope = physical display count > 1**, independent of `flyOn`. One monitor → misplacement impossible → literally today's code path. `flyOn: 'main'` on two monitors → still gated (its one overlay is still yankable).
4. **Backstop = `START_LEAD_MS + 5 × 300ms` from creation** (2200ms) — both numbers pre-existing and receipted, per the ticket's constraint. It only matters if the CLI hangs (normal retry exhaustion settles by itself); when it fires, the flight proceeds on whatever displays are correct.
