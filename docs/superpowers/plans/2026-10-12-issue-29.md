# Settings window (Alcove-style) — Implementation Plan (jiraPlane #29)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement
> this plan. Steps use checkbox (`- [ ]`) syntax for tracking. Multi-task plan: per
> AGENTS.md, build on ticket branch `issue-29` with **one commit per approved task**
> (Tasks 2–3; Task 1 produces only git-ignored variants, nothing to commit).
> **Task 1 ends at an owner gate.** Do not start Task 2 until the owner has picked a variant
> and the "Round-1 pick" section below is filled in. If the session ends at that gate, that is
> a natural seam: a fresh session picks up at Task 2 from this file.

**Goal:** A singleton settings window (`settings.html`) opens from a new tray item
**Settings…**. It holds Test flight, Pause polling, Fly on and Launch at login (General),
Banner style (Appearance), and version + repo link (About). Every control takes effect live,
and the tray menu and the window always show the same state.

**Architecture:** `main.js` owns all state and all disk writes. The window loads one
self-contained `settings.html` through its own preload, `preload-settings.js`. The page sends
*intents* (`set('flyOn', 'main')`); main validates them, persists them through the existing
`saveSettings()`, and pushes the full resulting state back (`settings-state`). The page renders
only from pushed state, so a failed change snaps back to the truth. One function,
`refreshSurfaces()`, redraws the tray menu and pushes state to the window, so a change on
either surface shows on both. Launch at login wraps `scripts/install-login-launch.sh` and
checks whether the app is itself the launchd job before it runs `launchctl bootout`.

**Tech Stack:** Electron 43 (`BrowserWindow`, `ipcMain`, `contextBridge`), vanilla HTML/CSS/JS
in one file, POSIX `sh`, `/bin/launchctl`. No new dependency.

**Spec:** `docs/superpowers/specs/2026-08-10-settings-window-design.md` (owner-approved
2026-08-10). Read it first. Read issue #29 too:
`gh issue view 29 --json body,comments` (the plain `--comments` form prints only comments). The
owner's 2026-09-24 comment on #29 changes the scope. See decision 1.

## Global Constraints

Copied from the spec, issue #29 and AGENTS.md. Every task inherits these.

- Settings visuals live in ONE self-contained `settings.html`: inline CSS/JS, system fonts, no
  external assets. Flight visuals stay in `plane.html`, untouched by this ticket.
- The renderer never touches disk. All persistence goes through `main.js`; `saveSettings()`
  stays the single writer of `settings.json`.
- Standard titled window: traffic lights, not resizable. None of the overlay machinery: no
  `'screen-saver'` level, no `releaseFromTilingWM`, no click-through.
- Singleton. Settings… refocuses an open window. Close hides the window. The app stays
  tray-only (dock stays hidden).
- Pre-agreed cut-line: if the ticket will not fit, drop Task 3 (Launch at login). The
  installer script keeps working standalone. Task 2 ships without the row; nothing else
  changes.
- Mind the #7 single-instance-lock gotcha: toggling launch at login must never leave zero or
  two running instances.
- Build in the main checkout, not a worktree. The installer writes its own repo path into the
  plist, so a worktree build would point the LaunchAgent at the worktree.
- No test suite. Verify = run the app. One running app instance at a time. Subagents never
  launch the app. Stop what you start.
- Test flights send a real [TEST]-marked Teams DM. Prefix runs with `TEAMS_WEBHOOK_URL=` while
  iterating.
- Commits: `summary (refs #29)`, no type prefix, never `fixes #29`. Trailer: the harness
  default `Co-Authored-By` line, nothing else. No commit hook.
- Issues and commits are written as if public: no env values, credentials, or personal data.

## Decisions the owner may want to overturn

1. **The native tray menu keeps its items and gains `Settings…`.** Done-when #1 ("Tray menu is
   exactly Test flight / Settings… / Quit") was superseded by #36 in the owner's 2026-09-24
   comment on #29. The #36 slices plan for these items to stay: #38 keeps today's menu as a
   right-click fallback "until #29 gives them a home", and #41 deletes Banner style, Fly on and
   Pause polling from `buildMenu()`. So after this ticket the menu is: Test flight · Replay ·
   Banner style ▸ · Fly on ▸ · — · Pause polling · — · **Settings…** · Quit. The menu and the
   window show the same state; each redraws when the other changes something.
2. **Pause polling stays session-only.** It is not written to `settings.json`. A restart comes
   back unpaused, same as today. Basis: the spec says "same semantics as today", and #39
   (owner, 2026-09-24) says "No persistence of pause state (it is session-only today; keep it
   so)". So Done-when #2 ("every control … survives restart via settings.json") is read as:
   Banner style and Fly on survive through `settings.json`, Launch at login survives as the
   plist itself, and Test flight is a button with no state. If the owner wants pause to
   persist, that is a one-field change to `saveSettings()` and the settings read, but a
   crash-restarted login instance would then stay paused with no visible sign.
3. **Launch at login, when the toggle runs inside the login instance itself.** `launchctl
   bootout` sends SIGTERM to the job's process, and here that process is this app. Bootout
   would leave zero instances. So:
   - **Off, from the login instance:** delete the plist only. The launchd job stays loaded
     until logout. Next login does not start the app. Side effect: if the app crashes before
     logout, launchd still restarts it (KeepAlive). Tray Quit still quits.
   - **On, from the login instance** (only possible after an Off in the same session): rewrite
     the plist only (`install-login-launch.sh --write-only`). The job is still loaded.
   - **From a dev instance:** Off runs `launchctl bootout` (the job is not this process, so
     nothing running is killed) and deletes the plist. On runs the full installer. launchd
     then starts a second instance, which loses the single-instance lock and exits with code
     0. KeepAlive (`SuccessfulExit=false`) does not restart a clean exit, so one instance
     remains. Task 3 proves that exit-0 fact on this machine before the code depends on it.
   - "Am I the login job?" = `launchctl print gui/<uid>/com.jiraplane.app` reports
     `pid = <process.pid>`. This works because the plist launches the Electron binary
     directly, so the job's pid is the main process.
4. **A separate preload, `preload-settings.js`,** exposes `window.jiraPlaneSettings`. The
   overlay pages keep `preload.js` unchanged, so a flight page can never call the setters
   (including launch at login).
5. **`OPEN_SETTINGS=1 npm start` opens the window on launch.** One line next to the existing
   `TEST_FLIGHT=1` check. Without it the build agent cannot see the real window, because it
   cannot click the tray. Cheap to drop if the owner does not want it.
6. **Variants first, as Task 1 with an owner gate.** Three shapes (below). Window size and page
   background come from the pick (the spec says dimensions come out of the pick). All three
   use `titleBarStyle: 'hiddenInset'`: the sidebar runs full height under the traffic lights,
   which is the macOS Settings look Alcove has.
7. **Fly on ships live.** #28 landed, so the row is wired to `flyOn`, not disabled.

## The contract (every variant and `settings.html` code against this)

State, pushed by main. The page renders only from this:

```js
// { bannerStyle: 'cargo' | 'skywriter',
//   flyOn: 'all' | 'main',
//   pollingPaused: boolean,
//   launchAtLogin: boolean | undefined,  // undefined until Task 3: hide the row
//   version: string }                    // e.g. '0.1.0'
```

API on `window.jiraPlaneSettings` (from `preload-settings.js`), with a standalone fallback so
the file opens in a browser with no Electron. This block goes at the end of `<body>` in every
variant and in `settings.html`, verbatim:

```js
// Settings bridge (#29): intents go to main, state comes back. In a plain
// browser there is no preload, so a local stand-in echoes state for layout work.
const api = window.jiraPlaneSettings || standaloneApi();
function standaloneApi() {
  document.body.classList.add('standalone');
  let state = { bannerStyle: 'cargo', flyOn: 'all', pollingPaused: false,
                launchAtLogin: true, version: '0.1.0' };
  let onState = () => {};
  return {
    onState: (cb) => { onState = cb; cb(state); },
    set: (key, value) => { state = { ...state, [key]: value }; onState(state); },
    testFlight: () => console.log('standalone: test flight'),
    openRepo: () => console.log('standalone: open repo'),
  };
}
api.onState(render);
```

Each variant defines `render(state)`: an idempotent full redraw that sets every control from
`state` (`input.checked = state.pollingPaused`, the selected banner card, the selected fly-on
option, `loginRow.hidden = state.launchAtLogin === undefined`, the version text). Controls
call only `api.set(key, value)`, `api.testFlight()`, `api.openRepo()`. No `<a href>`: the repo
link is a button that calls `api.openRepo()`.

Labels match the tray menu: **Test flight**; **Pause polling** (toggle on = paused);
**Fly on**: All displays / Main display; **Launch at login**; **Banner style**: Cargo tag /
Skywriter; About: `jiraPlane <version>` and a GitHub button.

Window chrome (all variants): `titleBarStyle: 'hiddenInset'`. Reserve a top-left zone of about
80 × 40 px for the native traffic lights. Mark the top strip `-webkit-app-region: drag`, and
put `-webkit-app-region: no-drag` on any control inside it. `body.standalone` draws three fake
traffic-light dots in that zone and centers the window frame on a neutral backdrop. In
Electron that class is never set, so the same file works in both places.

```js
// Settings window (#29): a normal titled window, none of the overlay
// machinery. Created on first Settings…, hidden (never destroyed) on close.
const REPO_URL = 'https://github.com/godfreyponce/jiraPlane';
let settingsWin = null;

function settingsState() {
  return { bannerStyle, flyOn, pollingPaused, version: app.getVersion() };
}

function pushSettingsState() {
  if (settingsWin && !settingsWin.isDestroyed())
    settingsWin.webContents.send('settings-state', settingsState());
}

function openSettings() {
  if (settingsWin) return showSettings();
  settingsWin = new BrowserWindow({
    width: /* Round-1 pick */, height: /* Round-1 pick */, useContentSize: true,
    resizable: false, maximizable: false, fullscreenable: false,
    titleBarStyle: 'hiddenInset',
    backgroundColor: /* Round-1 pick */,
    title: 'jiraPlane Settings',
    show: false,
    webPreferences: { contextIsolation: true, sandbox: true,
                      preload: path.join(__dirname, 'preload-settings.js') },
  });
  // Close hides; a real quit (#31's flag) still closes it.
  settingsWin.on('close', (e) => {
    if (quitting) return;
    e.preventDefault();
    settingsWin.hide();
  });
  settingsWin.webContents.on('did-finish-load', pushSettingsState);
  settingsWin.once('ready-to-show', showSettings);
  settingsWin.loadFile('settings.html');
}

// Every show re-sends state: a window hidden for hours never shows stale values.
function showSettings() {
  pushSettingsState();
  settingsWin.show();
  app.focus({ steal: true }); // tray-only app: bring the window in front of the active app
}

// The page sends intents; main validates and persists, and the resulting
// state comes back through refreshSurfaces. The renderer never touches disk.
ipcMain.on('settings-set', (e, key, value) => {
  if (key === 'bannerStyle' && (value === 'cargo' || value === 'skywriter')) setBannerStyle(value);
  if (key === 'flyOn' && (value === 'all' || value === 'main')) setFlyOn(value);
  if (key === 'pollingPaused' && typeof value === 'boolean') setPollingPaused(value);
});
ipcMain.on('settings-test-flight', () => testFlight());
ipcMain.on('settings-open-repo', () => shell.openExternal(REPO_URL));
```

- [ ] **Step 3: The launch-at-login block (`main.js`)**

After the settings window block, add:

```js
// Launch at login (#29) wraps the #7 LaunchAgent: on = the plist exists.
const LOGIN_PLIST = path.join(app.getPath('home'), 'Library', 'LaunchAgents', 'com.jiraplane.app.plist');
const LOGIN_SERVICE = `gui/${process.getuid()}/com.jiraplane.app`;
const INSTALLER = path.join(__dirname, 'scripts', 'install-login-launch.sh');
let loginToggleBusy = false;

function setLaunchAtLogin(on) {
  if (loginToggleBusy || on === fs.existsSync(LOGIN_PLIST)) return pushSettingsState();
  loginToggleBusy = true;
  const done = (err) => {
    if (err) console.error(`launch at login: ${err.message}`);
    loginToggleBusy = false;
    pushSettingsState();
  };
  // launchctl print fails (exit 113) when the job is not loaded.
  execFile('/bin/launchctl', ['print', LOGIN_SERVICE], (notLoaded, stdout) => {
    // #7 gotcha: if this process IS the login job, bootout would SIGTERM it
    // and leave zero instances. Only the plist changes; the loaded job stays
    // until logout, so a crash before then still restarts the app.
    const isLoginJob = !notLoaded && new RegExp(`^\\s*pid = ${process.pid}$`, 'm').test(stdout);
    if (on) {
      // The full install bootstraps the job: launchd's new instance loses the
      // single-instance lock to this one and exits 0, and KeepAlive
      // (SuccessfulExit=false) does not restart a clean exit.
      execFile('/bin/sh', [INSTALLER, ...(isLoginJob ? ['--write-only'] : [])], done);
    } else {
      fs.rmSync(LOGIN_PLIST, { force: true });
      if (notLoaded || isLoginJob) return done();
      execFile('/bin/launchctl', ['bootout', LOGIN_SERVICE], done);
    }
  });
}
```
