# Quit with a non-empty flight queue exits promptly — Implementation Plan

> **For agentic workers:** this is a **single-task** plan for issue #31. Per `AGENTS.md`, a
> single-task plan **stays uncommitted in the working tree** — no ticket branch, no commits. Build
> it, run the verification below, report what you actually saw, and stop for the owner's gate 2.

**Goal:** Quitting the app while flights are queued destroys the active flight and discards the
rest of the queue, instead of flying every queued flight to completion before exiting.

**Architecture:** A `quitting` flag set on Electron's `before-quit` event, checked first in
`flyNext()`. The bug's whole mechanism is that quit destroys the active flight's windows, each
window's `'closed'` handler decrements a counter, and the last one calls `flyNext()` — which
happily creates the next flight's windows mid-quit. One guard at the top of `flyNext` severs
that chain; Electron's normal quit then proceeds with nothing re-creating windows.

**Tech Stack:** `main.js` only. No new dependency, no renderer change.

## How the bug works (traced 2026-08-10, don't re-derive)

- `main.js:73-87` — `flyNext()` guards on `activeFlight || flightQueue.length === 0`, shifts the
  queue, creates windows, and wires each window's `'closed'` to decrement `open`; the last
  `'closed'` sets `activeFlight = null` and calls `flyNext()` again.
- On `app.quit()` (tray Quit, `main.js:391`), Electron closes every window. The active flight's
  windows fire `'closed'`, the chain above runs, and the next queued flight's windows are created
  **during** quit — so quit stalls and the cycle repeats until the queue is empty (~26s per
  two-display flight, observed with an instrumented 10-flight queue during #21 verification).
- There is currently **no** `before-quit`/`will-quit` handler anywhere in `main.js` — nothing to
  merge with, the handler is new.

Why discarding the queue is safe: `dispatchEvent` (`main.js:316-319`) fires the Teams DM at
dispatch time, *before* the flight ever leaves the queue, and the poller advances `state.json`
before output. A queued-but-unflown flight has already delivered everything durable; only the
visual is dropped, which is exactly what quitting asks for.

## Decisions the owner may want to overturn

1. **Queued flights are discarded, not persisted.** The ticket's fix sketch says bail; nothing is
   saved for the next launch. If you'd rather the queue survive a restart, that's a new ticket —
   it needs the dedup/state story thought through.
2. **The active flight is cut off mid-air rather than allowed to finish.** Quit means quit; the
   alternative (finish the current flight, drop the rest) would keep the app alive up to ~26s
   after Quit is clicked, which is most of the original complaint.

```js
// Quit (#31): app.quit() destroys the active flight's windows, whose 'closed'
// handlers would launch the next queued flight mid-quit and keep the app
// alive until the whole queue drained. Queued flights are discarded — the
// Teams DM (if any) already went out at dispatch time and state advanced
// before output, so only the visual is dropped.
let quitting = false;
app.on('before-quit', () => { quitting = true; });
```
