# Settings window follow-ups: drop guard, refresh on focus — Implementation Plan (jiraPlane #44)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement
> this plan. Steps use checkbox (`- [ ]`) syntax for tracking. **Single-task plan:** the change
> stays uncommitted in the working tree of this worktree (branch `t3/rt-44`). Never commit,
> never merge to main. One stop: Step 7 is gate 2.

**Goal:** A file dropped on the settings window leaves `settings.html` in place, and the
window re-reads its state each time it gets focus.

**Architecture:** Two small changes, both from the ticket. `settings.html` calls
`preventDefault` on `dragover` and `drop`, so the window does not navigate to the dropped
file. `openSettings()` in `main.js` adds `settingsWin.on('focus', pushSettingsState)`, so a
plist changed by hand while the window is open shows on the next focus.

**Tech Stack:** Electron ^43.2.0, vanilla HTML/JS. No new dependency.

**Spec:** No design spec. The decision record is issue #44's body and its one comment
(`gh issue view 44 --comments`). It follows from the #29 final review
(`docs/superpowers/plans/2026-10-12-issue-29.md`).

## Decisions the owner may want to overturn

Most likely to be wrong first.

1. **The builder tests the focus refresh by moving the real plist, not by running the
   installer.** `LOGIN_PLIST` is fixed to `~/Library/LaunchAgents/com.jiraplane.app.plist`, so
   any test touches the owner's real file. The builder copies it to a backup, removes it,
   checks the window, then restores it and confirms with `cmp`. No `launchctl` call. The
   Done-when line "running the installer by hand" is the owner's run at gate 2 (Step 7).
   The other choice: the builder does not touch the plist, and the owner flies the whole focus
   check.
2. **The drop guard covers the settings window only.** The popover (`popover.html`) may
   have the same navigate-on-drop bug. The ticket does not name it, so it is not in scope. If
   the owner wants it, that is a new issue.
3. **No `ready-for-agent` label.** The owner typing `/run-ticket 44` was the confirmation.

## Review Focus

Inputs a happy-path run does not exercise. Each line names the step that pins it.

1. **A link or text dragged on the window (not a file).** Same navigate risk, same guard:
   the listeners are on all `dragover`/`drop` events, not only file drops. Pinned: Step 2
   (the listeners do not filter on `dataTransfer.types`).
2. **A drop on a control (a button, the switch).** The events bubble to `document`, so the
   guard still runs. Pinned: Step 2 (the synthetic events are dispatched on `body`, a child
   of `document`).
3. **Focus while a Launch-at-login toggle is in flight.** The focus push sends
   `fs.existsSync(LOGIN_PLIST)`, the same source `setLaunchAtLogin` reads, and `done()` pushes
   again at the end. The switch ends on the truth. Pinned: code read in Step 4.
4. **Focus right after a quit starts.** `pushSettingsState` already checks
   `isDestroyed()`. Pinned: code read in Step 4.
