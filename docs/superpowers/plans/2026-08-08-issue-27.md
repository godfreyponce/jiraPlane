# ONBOARDING step 3: make failure visible — Implementation Plan

> **For agentic workers:** this is a **single-task** plan for issue #27. Per `AGENTS.md`, a
> single-task plan **stays uncommitted in the working tree** — no ticket branch, no commits. Build
> it, run the verification below, report what you actually saw, and stop for the owner's gate 2.

**Goal:** Rewrite `docs/ONBOARDING.md` step 3 so a wrong host, a rejected token, and success each
produce visibly different output — and none produces silence — and give `.env.example`'s
`JIRA_BASE_URL` the same non-partially-replaceable placeholder.

**Architecture:** One curl command does all of it. `-sS` keeps the progress meter off but lets
curl's connection/DNS/TLS errors reach stderr; `-i` puts the status line and `X-AUSERNAME` header in
the output; a `tr | grep | head` filter reduces the result to at most four labelled lines. The
placeholder becomes `YOUR-JIRA-HOST` — no TLD, so there is no `.com` left stranded by a partial
find-replace, and leaving it untouched yields a DNS error that names the placeholder back to you.

**Tech Stack:** Markdown only. Commands use `curl`, `tr`, `grep`, `head` — all present on a stock
macOS, no `jq`, no `python3`.

## Global Constraints

Copied from issue #27's Constraints section; every step below inherits these.

- **Doc and `.env.example` only.** No code changes, no app behavior change.
- **Placeholders only.** No real hostname, username, or user key in the doc — those live in
  gitignored `.env`.
- **Keep the token inline in the curl command.** Do **not** add `read`, `pbpaste`, or any other
  indirection aimed at keeping the token out of shell history. All three were tried in the session
  that found this bug and each introduced a new silent-failure mode worse than the shell-history
  exposure it avoided: `read` inside a pasted block swallows the submit newline and yields an empty
  token; `pbpaste` loses the token the moment the reader copies the command.
- **Don't restructure the rest of `ONBOARDING.md`.** Step 3 and the matching `.env.example` line
  only. Steps 1, 2, 4, 5, 6 and "Known quirks" are not to be touched.
- Repo is public. Issues and docs stay written as-if-public.

## Evidence this plan is built on

Every claim below was run before this plan was written — do not re-derive them, but do re-run them
as verification (V1–V4).

| Command | Result |
|---|---|
| `curl -s … https://jira.example.com/…` (the doc as written today) | exit 6, **zero output** |
| `curl -s … https://jira.corp.com/…` (partial replace of `example`) | exit 28, **zero output**, after a full connect timeout |
| `curl -s … https://127.0.0.1:9/…` | exit 7, **zero output** |
| `curl -sS … https://127.0.0.1:9/…` | `curl: (7) Failed to connect to 127.0.0.1 port 9 after 0 ms: Couldn't connect to server` |
| `curl -sS -i … 'https://YOUR-JIRA-HOST/…' \| tr … \| grep … \| head -4` | `curl: (6) Could not resolve host: YOUR-JIRA-HOST` |
| the same pipeline over a canned Jira DC `/myself` response | exactly 4 lines: status, `X-AUSERNAME`, `"key":…`, `"name":…` — nested `groups` names correctly excluded |

Two notes worth carrying into the build:

- The partial-replace case (`jira.corp.com`) is **worse** than the ticket describes: the host
  resolves, so curl hangs for the whole connect timeout and *then* prints nothing. `-sS` alone fixes
  the silence — a `--connect-timeout` is **not** part of this change (no basis for picking a number).
- `head -4` is load-bearing, not decoration. Jira DC's `/myself` includes a `groups.items[]` array
  whose members carry their own `name` field, and at least one of them serialises with `self` first,
  so `"name":"confluence-users"` survives the grep. The cap keeps it out, because the top-level
  `key` and `name` always precede `groups` in the body. Do not remove it.

## Decisions the owner may want to overturn

Flagged here rather than buried in the diff.

1. **`-sS` rather than dropping `-s` entirely.** The ticket says "no bare `-s`". Dropping `-s`
   altogether also surfaces errors, but re-introduces the progress meter, and meter noise is exactly
   what makes people re-add `-s` later. `-sS` = quiet meter, loud errors.
2. **`YOUR-PAT` replaces `<your-PAT>`.** Not required by any Done-when item. Rationale: it matches
   the new `YOUR-JIRA-HOST` form, and angle brackets teach a habit that breaks the moment a
   placeholder lands outside quotes. Same line, no behavior change. Easy to revert if unwanted.
3. **An `HTTP/1.1 404` line is included in the failure tells.** Also not required by a Done-when
   item. It covers the reader whose Jira lives under a context path (`https://host/jira`), who would
   otherwise see a status code the doc never mentions. One line; drop it if it reads as scope creep.

### Task 1: Rewrite step 3 and the `.env.example` placeholder

- [ ] **Step 1: Replace `docs/ONBOARDING.md` lines 24–36 with this exact text**

Everything from the `## 3.` heading through the "silently stop matching" line. Do not alter the
blank line separating step 3 from `## 4. Pick your outputs`.

````markdown
## 3. Find your username and user key

Your username is what you log in with. Your user key is internal and non-obvious; the easiest way
to get it is to ask Jira who you are. Replace both ALL-CAPS placeholders — `YOUR-JIRA-HOST` is the
host you reach Jira at in the browser, no `https://` and no trailing slash:

```bash
curl -sS -i -H "Authorization: Bearer YOUR-PAT" \
  'https://YOUR-JIRA-HOST/rest/api/2/myself' \
  | tr ',' '\n' | grep -Ei '^HTTP/|^x-ausername:|"(name|key)":' | head -4
```

Four lines back means it worked:

```
HTTP/1.1 200
X-AUSERNAME: your-username
"key":"JIRAUSER12345"
"name":"your-username"
```

`name` is your `JIRA_USERNAME` and `key` is your `JIRA_USER_KEY`. Both matter for @mention
detection — get either one wrong and mentions silently stop matching. (You may see `HTTP/2 200`
instead if your Jira speaks HTTP/2; it's the number that matters.)

Anything else is one of three failures, and they look different on purpose:

- **`401` with `X-AUSERNAME: anonymous`** — you reached Jira and it rejected your token. Go back to
  step 2.
- **`curl: (6) Could not resolve host` or `curl: (7) Failed to connect`** — you never reached Jira
  at all. The host is wrong, not the token.
- **`404`** — you reached a web server but not Jira's API. Check the host, including any path your
  Jira sits under; some installs live at `https://host/jira`.

If your output matches none of those, drop the `| tr …` pipe to see the whole raw response.
````
