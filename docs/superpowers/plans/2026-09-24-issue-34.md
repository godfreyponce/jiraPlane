# Tray "Replay <KEY>" re-flies the most recent real flight — Implementation Plan

> **For agentic workers:** this is a **single-task** plan for issue #34. Per `AGENTS.md`, a
> single-task plan **stays uncommitted in the working tree**: no ticket branch, no commits. Build
> it, run the verification below, report what you actually saw, and stop for the owner's gate 2.

**Goal:** A tray row directly under Test flight re-flies the last real event the plane flew
(same banner, same clickable tag URL) with no second Teams DM. The row is disabled until a real
event has flown.

**Architecture:** One module-level variable, `lastFlown`, holds the last real event. It is set in
the plane-sink branch of `dispatchEvent`, and only for `assigned`/`mention`/`comment` events that
are not test flights. Setting it rebuilds the tray menu through the existing
`tray.setContextMenu(buildMenu())` call, the same one Pause polling uses. A new `replayFlight()`
next to `testFlight()` calls `enqueueFlight(lastFlown)` directly. It skips `dispatchEvent`, so
the Teams sink never sees the replay. The existing queue handles "replay while a plane is in the
air".

**Tech Stack:** `main.js` only. Electron `Menu` template. No new dependency.

**Spec:** GitHub issue #34 (`gh issue view 34`). Its decisions came from the owner's 2026-09-24
/idea rounds.

## Global Constraints

Copied from issue #34. Every step below inherits these.

- No new dependency, no persistence, no new file. `plane.html` untouched.
- In-memory only. No `state.json` or `settings.json` field. After a restart the row is disabled
  until the next real event.
- `buildMenu()` is already rebuilt on change (Pause polling does this). Reuse that path. Do not
  add a second menu-refresh path.
- Replayable = `type: 'assigned' | 'mention' | 'comment'` only. Excluded: test flights
  (`test: true`), `digest`, `reassigned`. A test flight must never overwrite the remembered event.
- Plane only. Replay calls `enqueueFlight`, never `dispatchEvent`, so no Teams DM goes out.
- Label `Replay <KEY>` (the real issue key) when armed. `Replay`, disabled, when nothing has flown.
- One running app instance at a time. Subagents never launch the app. Stop what you start.

## Decisions the owner may want to overturn

1. **The event is remembered when it is dispatched, not when it takes off.** The ticket points
   at the plane-sink branch of `dispatchEvent` (`main.js:325`), so that is where `lastFlown` is
   set. Effect: if one poll cycle returns two events, the row shows the second key while the
   first is still in the air, and a Replay click in that window queues a copy of a flight that
   has not flown yet. The alternative is to set `lastFlown` in `flyNext()` when an event leaves
   the queue. That matches "actually flew" exactly, but it puts menu logic inside the queue
   mechanics. The window is a few seconds and only on multi-event cycles, so this plan follows
   the ticket.
2. **Allowlist, not denylist.** The filter is `['assigned', 'mention', 'comment'].includes(type)`,
   copied from the ticket's decision. A future event type will not become replayable until
   someone adds it to the list. A denylist (`!== 'digest'`) would be one word shorter, but it
   would let new types in silently.

## How the code is wired today (read 2026-09-24, don't re-derive)

- `main.js:76-79` — `enqueueFlight(event)` pushes to `flightQueue` and calls `flyNext()`.
  `flyNext()` (`main.js:81-95`) returns early while `activeFlight` is set, so a second enqueue
  waits for the current flight's windows to close. "Replay queues behind" needs no new code.
- `main.js:185-187` — `createFlight(event)` derives the tag URL from `event.issueKey`, and
  `main.js:~260` passes `type`, `issueKey`, `snippet` to the page. It does not mutate `event`.
  Re-enqueueing the same object gives the same banner and the same URL.
- `main.js:324-327` — `dispatchEvent` has two sinks. The plane sink runs only when
  `poller.config?.plane ?? true` (false under `PLANE=0`) and the type is not `reassigned`. The
  Teams sink always runs. Under `PLANE=0` the plane branch never runs, so `lastFlown` stays
  `null` and the row stays disabled. That covers the `PLANE=0` Done-when with no extra check.
- `main.js:360-367` — `testFlight()` dispatches `{ type: 'assigned', issueKey: 'PROJ-142', ...,
  test: true }`. Its type is `assigned`, so the allowlist alone would accept it. The
  `!event.test` check is what keeps it out.
- `poller.js:~315` — the flood-valve digest is `{ type: 'digest', issueKey: '', ... }`. The
  allowlist excludes it.
- `main.js:369-401` — `buildMenu()` returns a fresh template each call. Pause polling rebuilds
  with `tray.setContextMenu(buildMenu())` (`main.js:395`). `tray` is set in `whenReady`
  (`main.js:408`) before `startPolling()` runs, so `tray` is never null when `dispatchEvent` runs.

- [ ] **Step 2: Remember real events at the plane sink and rebuild the menu**

```js
function dispatchEvent(event) {
  if ((poller.config?.plane ?? true) && event.type !== 'reassigned') {
    enqueueFlight(event);
    // Replay (#34): real assigned/mention/comment only. Test flights and
    // digests fly but never become the replay target.
    if (!event.test && ['assigned', 'mention', 'comment'].includes(event.type)) {
      lastFlown = event;
      tray.setContextMenu(buildMenu());
    }
  }
  teams.sendForEvent(event).catch((e) => console.error(`teams sink failed: ${e.message}`));
}
```
