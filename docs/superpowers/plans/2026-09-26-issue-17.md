# Constant wall-clock flight duration — Implementation Plan

> **For agentic workers:** this is a **single-task** plan for issue #17. Per `AGENTS.md`, a
> single-task plan **stays uncommitted in the working tree**: no ticket branch, no commits. Build
> it, run the verification below, report what you actually saw, and stop for the owner's gate 2.

**Goal:** A multi-display flight takes the same time as a single-screen flight. On a wider row,
the plane flies faster; the flight does not get longer. Single-display flights stay exactly as
they are today.

**Architecture:** `createFlight` in `main.js` sets each row's duration, `durMs`, from the width of
the whole row today. After this change it uses the width of the row's reference display, `ref`.
`ref` already exists: it sets the flight line `flyY` and the skywriter text bounds. The renderer
does not change. `plane.html` gets speed only as `(toX − fromX) / durS`, from `dur`, `minX` and
`maxX`. So a shorter `dur` over the same `minX..maxX` is a faster plane, and the swoop period
(`durS / 2`), the audio envelope, the skywriter timing and the #15 drag re-seed all follow it.

**Tech Stack:** `main.js` only. No new dependency.

**Spec:** GitHub issue #17 (`gh issue view 17 --comments`). Owner decision in the comment
(2026-08-10): **Option 1 — constant wall-clock**, computed per flight in `createFlight`, no
onboarding step, no user setting, no speed cap for now.

## Decisions the owner may want to overturn

1. **The target is "the reference display alone", not a literal 10 seconds.** The ticket says
   "the accepted ~10s". That number is from before #6. Commit `9438763` (2026-08-02) changed
   the exit margin from 40px to 400px, so the towed tag clears the screen. Since then a flight
   on the 1512pt dev screen takes (1512 + 194 + 400) / 175 = **12.03 s**, and #6, #11, #15 and
   #28 were all accepted at that duration. A flat 10 s would change every single-display flight:
   12.0 → 10.0 s on the dev screen, and 14.4 → 10.0 s on a 1920pt coworker screen. That breaks
   Done-when #3. This plan keeps the 12.03 s. If the owner wants a literal 10 s, the one-line
   change is `const durMs = FLIGHT_MS` with `FLIGHT_MS = 10000`, but then single-display flights
   change too, and Done-when #3 must be rewritten.
2. **The reference display is the row's existing `ref`**: the primary if the primary is in the
   row, else the row's tallest display. It already sets `flyY` and the skywriter text bounds, so
   this plan adds no new concept. On the owner's desk (1512pt built-in at 0,0 = primary, 1920pt
   external at 1512,−98) the flight takes 12.03 s at ~335 px/s, 1.9× the single-screen speed.
   The alternative is the widest display in the row. On the same desk that gives 14.37 s at
   ~280 px/s, a calmer plane, but a single-display flight on the primary would then be shorter
   than a flight that also crosses the external.
3. **No `design-directions/` variants.** The standing visual habit (#3/#4) is for choosing a look.
   Here the owner chose the rule on 2026-08-10, the look does not change, and Done-when #4
   requires a real two-display flight. A browser mock-up cannot show that.

## How the code is wired today (read 2026-09-26, don't re-derive)

- `main.js:16-18`: `SPEED_PX_S = 175`. Its comment says a 1512-DIP screen plus ~234px of
  margins crosses in 10 s. That was true before `9438763` changed the margins.
- `main.js:186-217`: `createFlight` maps `partitionRows(displays)` to row objects. Inside the
  map, `ref` is computed at `main.js:203-204`, then `main.js:209-213` computes
  `spanPx = maxX + 400 - (minX - 194)` and `durMs = Math.round((spanPx / SPEED_PX_S) * 1000)`.
  The row object returned at `main.js:215` carries `durMs`, and `ref` too.
- `durMs` is used in exactly three places. All three read `row.durMs` and do not change:
  the `dur` query param (`main.js:~269`), `rowEndAt.push(... start + row.durMs)` (`main.js:289`),
  and the gated finalize `rowEndAt = rows.map((row) => startAt + row.durMs)` (`main.js:303`).
- `plane.html:276-287`: `durS` comes from `dur`. `courseX(s) = fromX + (s / durS) * (toX - fromX)`
  with `fromX = minX − 1.1 × rig width` and `toX = maxX + 400`. Speed is not a parameter.
- `plane.html:571-597` (#15 re-seed) inverts `courseX` with the same `durS`/`fromX`/`toX`, and
  the fast exit runs at `EXIT_RATE = 4` × cruise. Both scale with the new cruise speed
  automatically. Do not edit them.
- `plane.html:401-403` (audio) and `plane.html:440-462` (skywriter) read the same `dur`.

**Byte-for-byte proof for single-display rows:** for a one-display row, `minX = d.bounds.x`,
`maxX = d.bounds.x + d.bounds.width`, and `ref = d`. The old span is
`x + w + 400 − (x − 194) = w + 594`. The new span is `ref.bounds.width + 194 + 400 = w + 594`.
Electron display bounds are integer DIPs, so the result is the same integer, the same division
and the same `Math.round`. The `durMs` value does not change.
