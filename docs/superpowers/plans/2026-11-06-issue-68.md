**Goal:** README, ONBOARDING, and `package.json` stop saying macOS only. ONBOARDING gets a Windows
path, and a fresh clone on the Windows VM follows that path to a real Jira flight and a real Teams DM.

**Architecture:** Docs and one `package.json` string. No app code changes. ONBOARDING keeps Mac

Each W step either gives the Windows commands or says "same as step N". The proof is a run on the
VM from a fresh clone of `origin/main`, after #67 has landed there.

**Tech Stack:** Windows PowerShell 5.1 (in the box on Windows 11), `curl.exe` (in the box),
`npm.cmd`, Electron 43.2.0, the VM commands in `docs/windows-vm.md`.

**Spec:** GitHub issue #68 (`gh issue view 68 --comments`). Parent #60 holds the decisions. #69
(Visual C++ runtime) is folded in, see decision 4. #67 is open at planning, see decision 3. No

## Decisions to check at gate 1

1. **ONBOARDING gets one `## Windows` section at the end, steps W1 to W7.** Mac steps 1 to 7 stay
   unchanged, as the constraint asks. The panel already says `See ONBOARDING § 7.` for the Mac, so
   the Mac numbering must not move. #67's panel points Windows users to **`ONBOARDING § W7`**. That
   name is the contract between the two tickets. Put a comment on #67 that names it (Step 4). The
   alternative is a Mac block and a Windows block inside each step. It reads better for one
   platform at a time, but it edits every Mac step and puts the § 7 pointer at risk.
2. **Every Windows command runs in Windows PowerShell, and npm is called as `npm.cmd`.** This was
   measured on the VM at planning. The execution policy is `Restricted`, the Windows default, so
   plain `npm` runs `npm.ps1` and fails with `running scripts is disabled on this system`.
   `npm.cmd -v` printed `11.20.0` in the same window. A work PC may not let a user change the
   policy, so the docs do not ask for that. The cost: `npm.cmd` looks odd, so W1 explains it in one
   sentence. The alternative is Command Prompt for git and npm and PowerShell only for W3. That is
   two shells in one walkthrough.
3. **The docs get written now. The VM run waits for #67 on `origin/main`.** The owner picked this
   (option 2, 2026-11-06). Without #67, the fresh clone's update check fails on Windows, and the
   run would prove a build the coworker will not get. If #67 is not on `origin/main` when this plan
   is built, the build does Steps 1 to 6, skips 7 to 14, and stops at gate 2 with the VM boxes
   open. A second build session then runs Steps 7 to 15 after #67 lands. **This is the decision
   most likely to be wrong:** it can split the ticket over two sessions.
4. **#69 is folded into W1.** Both of #69's boxes are a sentence in W1: the Visual C++
   Redistributable for x64 and for Arm64, and how the failure looks. #69 closes with #68 at accept.
   The x64 package name comes from #69 and has not been tested.
5. **The owner types the real secrets. The agent never reads or moves them.** The owner runs W3
   with their own token in the VM and fills the VM's `.env` in Notepad from W5. The agent never
   copies the Mac's `.env`, never prints the VM's `.env`, and deletes it in Step 13. This keeps the
   doc test honest too: a person follows the steps, not the agent who wrote them.
6. **The run also covers a real flight under the login start (W6).** #66 left "a real Jira reply
   under the login start" for #68. It costs one VM restart and one more Jira comment. The login log
   is the only place where the agent can read a real flight line, because the W5 instance writes to
   the owner's PowerShell window.
7. **W7 is not run end to end.** The newest tag is `v0.1.5`, which is older than the Windows port,
   so checking it out on Windows gives an app that crashes at start. W7 only works after the owner
   cuts the next release at accept. The run tests W7's fetch and tag-name lines. It also tests the
   "quit first" line, because Windows locks Electron's files while the app runs.

script`):

  because running scripts is disabled on this system`. `npm.cmd -v`: `11.20.0`.
- PowerShell `5.1.26100.9711`. `curl.exe` is `C:\WINDOWS\system32\curl.exe`.
- The W3 command below, against the literal host `YOUR-JIRA-HOST`, printed
  `curl: (6) Could not resolve host: YOUR-JIRA-HOST`. Against `https://example.com/rest/api/2/myself`
  it printed `HTTP/1.1 404 Not Found`. Both match Mac step 3's failure list. The success form has not

- `%USERPROFILE%\jiraPlane` exists (the #61 rig clone, `core.autocrlf=false`). No `jiraPlane` value
  under `HKCU\...\Run`. No `electron` process.

In the repo: `poller.js:27` trims trailing whitespace on each `.env` line (`\s*$`), so a CRLF `.env`
from Notepad or a normal Windows clone parses. The worktree has no `.env` and no `node_modules`.

## Review Focus

1. **A reader on a locked-down work PC.** They cannot change the execution policy and may not have
   admin rights for winget. W1 uses `npm.cmd` and says that Windows may ask to allow the installs.
   Covered by Step 8, which runs W1 as written.
2. **A normal Windows clone converts line endings to CRLF.** The rig clone turned this off, so CRLF
   has never been run. The fresh clone in Step 8 uses W1's plain `git clone`, so Steps 9 to 11 run
   with CRLF files.
3. **The tray icon hides behind `^` on a new install.** A reader who sees nothing thinks the app did
   not start. W5 says where to look. Step 9 records where the icon appeared.
4. **The first poll seeds silently.** A self-triggered comment made before the first cycle ends gets
   absorbed by the seed, and no plane flies. Step 10 waits for `state.json` before the owner comments.
5. **A reader updates while the app runs.** Windows locks Electron's files, so `npm.cmd install` can
   fail part way. W7 says to quit first. Step 12 shows what happens when this is skipped.
