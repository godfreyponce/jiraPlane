# App starts on Windows and flies a test flight (#62) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this
> plan. Steps use checkbox (`- [ ]`) syntax for tracking. **Two tasks, so one commit per task on
> branch `issue-62`.** The commits are what the coworker clones, so this plan must not collapse to
> one uncommitted task. Two stops: Final Step 3 (owner watches the VM) and Final Step 4 (gate 2).
> Run every launch and stop yourself. Do not hand one to a sub-subagent.

**Goal:** On Windows the app starts, shows a tray icon that can be seen on a dark and a light
taskbar, and flies one test flight, with Mac behavior unchanged.

**Architecture:** Two guards remove the two startup crashes. Windows has no template images, so a
small function picks the existing black plane or a new white plane from the taskbar's own dark or
light mode, and re-picks when that mode changes. The white plane is the one the popover stage
already draws. Everything else in the path to a flight already survives on Windows, by reading: see
"What was checked".

**Tech Stack:** Electron 43.2.0 (`nativeTheme`, `Tray`, `nativeImage`), `rsvg-convert` (the #52
tool), the Windows VM commands in `docs/windows-vm.md`.

**Spec:** GitHub issue #62 (`gh issue view 62`). Decisions and fog: parent #60. No design spec.

## Decisions to check at gate 1

1. **Two icon files switched by taskbar mode, not one tinted icon.** The black plane is today's file
   and the white plane is `popover.html:226-228` with the same paths and opacities, so no new art
   and no color is invented. Each gets the strongest contrast its taskbar allows. The cost is about
   six lines and one more moving part. The alternative is one mid-blue plane: one line of code, no
   theme logic, but a color the owner never picked and much weaker contrast on both taskbars.
2. **Done when 1 cannot be proved from the log alone.** On Windows, Electron 43.2.0 reports an
   uncaught main-process exception only as a dialog (`lib/browser/init.ts:23-37`,
   `shell/browser/ui/message_box_win.cc:349`), and nothing reaches stdout or stderr. So box 1 is
   checked by three things: the log holds the flight line and no error text, `electron` is still
   running after the flight, and the owner sees no error dialog on the VM. No code is added. The
   alternative is a Windows-only `process.on('uncaughtException')` logger, but having a listener
   stops the dialog, and the coworker would then see nothing go wrong.
3. **Two tasks so the branch can be pushed before accept.** A single-task plan stays uncommitted,
   and the coworker cannot clone that. The owner pushes `issue-62` at gate 2 (agents cannot push).
   This puts the branch on the public repo before accept, with no `.env` and no secrets in it. It
   does not touch `main`.
4. **`process.getuid?.()` leaves `gui/undefined/...` in `LOGIN_SERVICE` on Windows.** It is the
   smallest guard, and the string never reaches `launchctl`, because `/bin/launchctl` is not there:
   `execFile` calls back with ENOENT. The Settings login toggle on Windows therefore logs an error
   and does nothing until #66 replaces it.
5. **PNG, not ICO.** Electron's docs recommend ICO on Windows "to get best visual effects". The
   box asks for visible, and the 16 and 32 px pair is what #52 made and proved. At 125% or 150%
   display scale the icon may look slightly soft. An ICO is a follow-up if the owner dislikes it.

The `# Visual rule` variant round does not apply: the ticket says "No 3-variant round for the icon."

- [ ] **Step 1: Make the white plane**

`assets/iconWhite.svg` is `assets/iconTemplate.svg` with `#000` replaced by `#fff`. Then:

```bash
rsvg-convert -w 16 -h 16 assets/iconWhite.svg -o assets/iconWhite.png && rsvg-convert -w 32 -h 32 assets/iconWhite.svg -o assets/iconWhite@2x.png
```

Do not use "Template" in these names. Electron finds `@2x` by name on Windows too.

- [ ] **Step 2: Check the pixels**

```bash
magick assets/iconWhite.png -format '%wx%h %[fx:maxima.r] %[fx:minima.r]\n' info: && magick assets/iconWhite@2x.png -format '%wx%h %[fx:maxima.r] %[fx:minima.r]\n' info: && git diff --stat main -- assets/iconTemplate.png assets/iconTemplate@2x.png assets/iconTemplate.svg
```

Expected: `16x16` and `32x32`, and no change to the template files. Then montage both new PNGs on
`#262626` and look at the result: the wing fold must show, as it did in #52's montage. Keep the
montage in your scratchpad, not in the repo.

- [ ] **Step 3: Write `trayIcon()` and wire it in**

`trayIcon()` returns `nativeImage.createFromPath` of `assets/iconWhite.png` when
`process.platform === 'win32' && nativeTheme.shouldUseDarkColorsForSystemIntegratedUI`, and of
`assets/iconTemplate.png` otherwise. Its one comment gives the why: Windows has no template images,
and the taskbar's mode can differ from the apps' mode.

In `whenReady`: `tray = new Tray(trayIcon());`. Right after it, inside
`if (process.platform === 'win32')`: `nativeTheme.on('updated', () => tray.setImage(trayIcon()));`.
The Mac registers no new listener and loads the same file.

- [ ] **Step 4: Prove the taskbar flip line, with no owner yet**

Sync, then start with `TEST_FLIGHT=1 TEAMS_WEBHOOK_URL=`. With the app still running:

```bash
ssh windows-vm 'reg add HKCU\Software\Microsoft\Windows\CurrentVersion\Themes\Personalize /v SystemUsesLightTheme /t REG_DWORD /d 0 /f && powershell -NoProfile -Command "Stop-Process -Name explorer -Force"'
```

Restarting Explorer is what makes the taskbar redraw. Wait a few seconds, then
`ssh windows-vm 'powershell -NoProfile -Command "Get-Process explorer,electron | Format-Table Name,Id,SessionId; reg query HKCU\Software\Microsoft\Windows\CurrentVersion\Themes\Personalize /v SystemUsesLightTheme"'`.
Expected: `explorer` is back in the desktop session, `electron` is still there, and the value is
`0x0`. If Explorer does not come back or the flip line is otherwise wrong, change it and say so in
the gate 2 report. If you cannot make it work, ask the owner to set the mode on the VM by hand.

- [ ] **Step 5: Try to see it yourself**

If the Parallels window is on the Mac's screen, capture it with `screencapture -x` and read the
