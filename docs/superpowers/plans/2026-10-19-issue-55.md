> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Answer #55 yes or no, with window-probe evidence from two displays with AeroSpace
running. No lasting code: the spike patch is reverted before gate 2.

**Architecture:** A throwaway, env-guarded patch to `main.js` can (a) skip
`releaseFromTilingWM` on the overlays and (b) set `closable: false` on them, with the
`before-quit` `setClosable(true)` repair the ticket names. Each run launches the app with
`TEST_FLIGHT=1` while AeroSpace's focus is on one chosen monitor, then probes the overlay
windows 1 s and 3 s after the `flight:` log line. The probe reads three things: where the
window server has each overlay (CoreGraphics), whether AeroSpace lists it, and how AeroSpace
classifies it (`aerospace debug-windows --window-id`, which prints `AXCloseButton` and
`Aero.AxUiElementWindowType`). A control run (release skipped, closable left at its default)
must show the yank first. If the control does not go red, the probe can't tell the cases
apart, and the spike stops.

**Why this is an open question, not a repeat:** #6's elimination trail (issue #6, "Elimination
trail" and "Mechanism") says it tried `closable: false` on the overlays one variable at a time,
and the yank survived. It also says Chromium exposes `AXCloseButton` even with
`closable: false`. STATE.md's AeroSpace gotcha repeats that. #54 then found the panel with
`closable: false` is a popup to AeroSpace 0.21.3. Electron (`^43.2.0`) and the accessory
policy (`app.dock.hide()`) were the same at #6. The panel differs from the overlays in
`type: 'panel'`, `minimizable: false`, `maximizable: false`, `vibrancy`, and in having no
`transparent`/`focusable: false`. AeroSpace's rule (`isWindowHeuristic`,
`Sources/AppBundle/model/AxUiElementWindowType.swift`): an accessory app's window with no
close button is a popup. So the deciding fact is whether the overlay's AX tree has an
`AXCloseButton` under `closable: false`. The probe reads exactly that.

**Tech Stack:** Electron 43 (`BrowserWindow` options, `setClosable`), AeroSpace 0.21.3-Beta CLI
(`list-monitors`, `list-workspaces`, `workspace`, `list-windows`, `debug-windows --window-id`),
the CoreGraphics window probe (osascript JXA).

**Spec:** GitHub issue #55 (`gh issue view 55`). Background: issue #6 (mechanism), HISTORY.md

## Overlays as AeroSpace popups: `closable: false` alone is not enough — #55 (2026-10-19) — ACCEPTED & CLOSED; no code (spike)

The question was whether `closable: false` on the flight overlays makes AeroSpace treat them
as popups, as it does the tray panel since #54, so the overlays could drop
`releaseFromTilingWM`. Alone, it does not: the overlay still has an `AXCloseButton`,
AeroSpace classifies it `dialog`, adopts it, and moves both overlays to the focused monitor.
With `minimizable: false` and `maximizable: false` added (the panel's other two flags), the
`AXCloseButton` is gone, the overlays are `popup`, AeroSpace lists neither, and each stays on
its own display. The spike patch was reverted; nothing shipped.

- **Proven:** worktree, two displays (built-in 1512x982@0,0, external 1920x1080@1512,0),
  AeroSpace 0.21.3, release skipped by an env-guarded patch, focus on each monitor in turn,
  probes 1 s and 3 s after the `flight:` line. Control (closable default): both overlays on
  the focused monitor's workspace (2 or 8), `AXCloseButton` present, type `dialog`. `closable:
  false` alone: identical to the control in both directions. Plus `minimizable`/`maximizable:
  false`: `AXCloseButton: null`, type `popup`, parent `MacosPopupWindowsContainer`, no
  workspace, not in `list-windows`, built-in overlay at `0,0 1512x982` and external at
  `1512,0 1920x1080` at both probes, both directions. Every run exited within 1 s of SIGTERM
  mid-flight (with `before-quit` calling `setClosable(true)` on live overlays), all at layer 1000.
- **What the plan got wrong:** nothing. #6's "closable:false doesn't help" was true of
  `closable` alone; the panel's two extra flags are the difference.
- **Deferred:** the removal itself (draft title: "Overlays become AeroSpace popups —
  closable/minimizable/maximizable false, drop releaseFromTilingWM"), not filed; the owner
  decides. Not covered: which of `minimizable`/`maximizable` is needed (both changed at
  once), stacked displays, one display, the #9 tag click and #11/#15 drag under these flags,
  and the tray Quit path (only SIGTERM was run).
