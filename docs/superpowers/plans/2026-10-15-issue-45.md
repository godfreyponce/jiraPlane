## Decisions the owner may want to overturn

1. **#45 builds before #35.** #45's constraint says "after #35 lands, or fold it into #35's
   rewrite". #35 is open, unlabeled, and not `next_action`; #45 is. So #45 adds a self-contained
   section now, in #35's target style (command alone in a fence, one "you should see" sentence),
   and #35's rewrite later carries it over under its own "every command still appears" rule.
2. **Login restart = re-run the installer.** Alternative: `launchctl kickstart -k
   gui/$(id -u)/com.jiraplane.app`. Rejected: it is a second thing to learn, it fails when the
   job is not loaded (a coworker who tray-Quit earlier), and the installer header already says
   "Re-run after moving the repo". The installer covers running, quit, and never-installed alike.
3. **The verification does not stage an older commit in `~/Developer/jiraPlane`.** The evidence
   that the restarted instance runs the pulled code is: new pid, process start time later than
   the `git pull`, and Electron reading `main.js` only at launch. The visible proof (right-click
   the menu-bar plane opens the popover, not a menu) is the owner's at gate 2, because the agent
   cannot click the tray. Checking out `aaa412f` (pre-#41) first would give a visible before/after
   but means rewriting the owner's working checkout; not worth it for a docs ticket.
4. **The login instance is left running at gate 2.** It is the owner's own login job, restarted
   by the documented step, and the owner needs it up to do the right-click check. Pre-session
   state was: plist present, job not loaded (`launchctl print` exit 113), no instance running.
   To return to that state: `launchctl bootout gui/$(id -u)/com.jiraplane.app`.
5. **The coworker note is posted as an issue comment during the build**, not held for accept.
   Done-when 4 says "drafted in this issue". The owner edits it before sending; posting a draft
   is not landing code.
6. **The "you are on the new code" check in the doc is `git log -1 --oneline` plus right-click →
   popover.** The issue's example ("Settings… is in the tray menu") predates #41; after #41 there
   is no native menu, so the popover opening on right-click is the visible marker.

## Review Focus

Inputs the ticket implies but no step runs. One line each, most likely first; the owning step
is named.

1. **A terminal `npm start` is running when the coworker re-runs the installer.** launchd's new
   instance loses the lock, exits 0, and KeepAlive (`SuccessfulExit=false`) does not restart it:
   the coworker ends up with the old terminal instance and no login instance. The doc says to
   Ctrl-C the terminal first (Task 1 Step 2, "If a terminal `npm start` is running…"). Task 2
   Step 7 runs the lock case the other way round (login up, `npm start` prints "already
   running") as the cheap proxy.
2. **`npm install` replaces `node_modules/electron` while the login instance runs** (only when
   `package.json`'s electron version moved). macOS may kill a running app whose bundle changed
   under it; KeepAlive restarts a crash, on the new binary. Either way the next step restarts it.
   Not exercised (no electron bump on main); noted so the build session reports it if it bites.
3. **The coworker's checkout has local edits** (`.env` is gitignored, but someone may have
   touched `plane.html`). `git pull` refuses with "Your local changes would be overwritten".
   Out of scope for the doc; Task 1's "you should see" names the two normal outputs only.
4. **Coworker installed login launch from a different clone path than the one they pull in.**
   The plist's `ProgramArguments` points at the old path; re-running the installer from the
   current clone rewrites it. Covered by the chosen restart command (Decision 2), not by text.
5. **Coworker never did step 6 and never has a terminal open** (app started some other way).
   Not a real case: the two documented ways to start the app are `npm start` and the installer.

````markdown
## 7. Update

New features reach you only when you pull and restart. The app does not check for
updates, and a pull on its own changes nothing: the running instance keeps the old
code until it restarts.

```bash
git pull
```

You should see a list of changed files, or `Already up to date.`

```bash
npm install
```

You should see `up to date` or `added N packages`, and no errors.

Now restart the instance that is running. Which command depends on how you started it.

**Started from a terminal with `npm start`:** press Ctrl-C in that terminal, then run
`npm start` again. The plane icon leaves the menu bar and comes back.

**Started at login (step 6):** re-run the installer. It stops the running login instance
and starts a fresh one on the code now on disk. It also works if you quit the login
instance earlier and nothing is running.

```bash
./scripts/install-login-launch.sh
```

You should see `Installed com.jiraplane.app — jiraPlane is now running and will start at
every login.` and the plane icon leave the menu bar and come back.

If a terminal `npm start` is running at the same time, Ctrl-C it first. Otherwise the new
login instance finds the lock held, exits, and launchd does not start it again.

To check you are on the new code, run `git log -1 --oneline` and right-click the plane icon.
The popover opens (builds before 2026-10-15 show a plain menu instead), and the commit
printed is the one that is running.
````
