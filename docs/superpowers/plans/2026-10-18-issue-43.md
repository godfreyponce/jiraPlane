# A mention added by editing an older comment flies (#43) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A comment that was created before the lookback window, edited inside it to mention
the owner, and never flown, flies as a `mention` on the next cycle. The #13 backlog guard and
the seen-set dedup keep working.

**Architecture:** One change in `collectRelevantComments()` (`poller.js:177-205`). Today the
loop drops every comment whose `created` is before `cutoff`. After the change, a comment is
kept if it was **created** inside the window (as now), **or** if it was **edited** inside the
window (`c.updated >= cutoff`) **and** its current body mentions the owner. Jira DC's comment
JSON already carries `updated`. When a comment was never edited, `updated` equals `created`.
The window check moves below the `mentionsMe(body)` call because it now needs `mentions`.
Nothing else changes: the JQL, the flood valve, `cycle()`, and the state shape stay as they are.

**Tech Stack:** Node 24 (`fetch` is global), Jira DC REST v2 comment JSON (`created`,
`updated`, `body`, `author`).

**Spec:** GitHub issue #43 (`gh issue view 43`). Background: the #13 entry in
`docs/HISTORY.md` ("Pre-existing comment flood guard").

## Decision the ticket asks the plan to make (Done when, item 4)

**An edit to an old, never-flown, non-mention comment on a ticket assigned to you does NOT fly.**
Only an edit that leaves a mention in the body rescues an old comment.

Why: the poller cannot see what an edit changed. Jira DC keeps no edit history, so a typo fix
looks the same as new content. If edits fly as `comment`, then on a newly assigned ticket any
edit to any old backlog comment (for example during the hand-off) flies, and #13's guard leaks.
A mention is different: it is addressed to you, and you never got it. If an edit fixes a typo in
an old comment that already mentioned you and never flew (for example because it was backlog when
the ticket came to you), that comment flies once. The plan accepts that cost.

## Review Focus

1. **Prune window re-fly.** `pruneSeen()` drops seen entries after `PRUNE_DAYS` (30). A mention
   comment that flew more than 30 days ago and is edited today flies again. Before this change,
   the `created` check made that impossible. Accepted: it is rare, and it is still a mention. The
   harness does not pin this case. Gate 2 names it.
2. **Old comment beyond the newest 20.** `recentComments()` fetches the 20 newest comments by
   `created` (`COMMENTS_PER_ISSUE`). On a busy ticket, an old comment that gets edited may not be
   among them, and it does not fly. Out of scope for this ticket (do not change the fetch). Gate 2
   names it.
3. **Edit to a mention that already flew** must not fly again. Harness scenario B pins this.
4. **A newly assigned ticket whose old backlog includes an unedited mention** must fly only
   `assigned`. Harness scenario C pins this.
5. **Missing `updated`.** A comment with `created` before the window and no `updated` field is
   dropped (it counts as not edited). Harness scenario E pins this.

## A mention added by editing an older comment flies — #43 (2026-10-18) — ACCEPTED & CLOSED; commit <hash>

`collectRelevantComments()` dropped every comment created before the lookback window (#13's
backlog guard), so a coworker's old comment, edited hours later to add a mention, never flew.
A comment now passes the window check when it was created inside the window, or when it was
edited inside the window (`updated >= cutoff`) and its current body mentions you. An edit to an
old comment that leaves no mention still flies nothing, even on a ticket assigned to you:
Jira DC keeps no edit history, so a typo fix looks the same as new text, and letting edits fly
as `comment` would leak #13's guard on every hand-off. One hunk in `poller.js`; the JQL, the
