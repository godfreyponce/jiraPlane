# Start at login on Windows (#66) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this
> plan. Steps use checkbox (`- [ ]`) syntax for tracking. **Single-task plan:** the work stays
> uncommitted in the working tree of this worktree (branch `issue-66`). Never commit, never merge
> to main. Three stops: Step 5 (owner clicks On), Step 8 (owner reads the VM and clicks Off), and
> Step 12 (gate 2). Run every launch and stop yourself. Do not hand one to a sub-subagent.

**Goal:** The Settings toggle starts the app at the next Windows login from a clone, shows the true
state, and the login-started app writes its console output to a per-user file, with Mac behavior
unchanged.

**Architecture:** On Windows, `setLaunchAtLogin` calls Electron's login item, which writes one value
under the `Run` registry key: `electron.exe`, the clone's folder, and a `--login-start` flag. The
flag is how the app knows it has no console, so at the top of `main.js` it sends its stdout and
stderr to a file. The Mac path is left as it is: the only Mac-side edit is that the settings state
reads through a small function with a platform check.

**Tech Stack:** Electron 43.2.0 (`app.setLoginItemSettings`, `app.getLoginItemSettings`,
`app.getPath`), the Windows VM commands in `docs/windows-vm.md`.

**Spec:** GitHub issue #66 (`gh issue view 66`). Decisions and fog: parent #60. No design spec.

## Decisions to check at gate 1

1. **No restart after a crash on Windows.** The ticket's constraint: login item, no Task Scheduler.
   If the app crashes, there is no plane and no Teams DM until the next login or a manual start. The
   Mac's `KeepAlive` has no match here. The owner accepted this on #60 and may overrule it now.
2. **The log file is `%APPDATA%\jiraplane\logs\jiraplane.log`.** `%APPDATA%\jiraplane` is the app's
   `userData` folder, and it already exists on the VM (checked at planning). So one folder holds
   everything the app keeps per user, and no second location is invented. The alternative is
   `%LOCALAPPDATA%`, which does not roam on a work PC. The cost of `%APPDATA%` is that a roaming
   profile would copy the log. The size is small: under 1 KB a day normally and about 85 KB a day if
   Jira is unreachable all day, by #19's numbers.
3. **The toggle reads `executableWillLaunchAtLogin`, not `openAtLogin`.** `openAtLogin` reads only
   the registry value named for the AppUserModelId and ignores the `name` option
   (`shell/browser/browser_win.cc:730`). `executableWillLaunchAtLogin` looks at every value for this
   clone's `electron.exe` and is false when the owner has switched the app off in Windows' Startup
   apps page (`:189-267`). That is the "true state" of Done when 2. The alternative is no `name`,
   which makes `openAtLogin` work, but the default name would be `electron.app.Electron`, because
   the name comes from the exe's product name (`shell/common/application_info_win.cc:36-40,61`). Any
   other Electron app run from source on that PC would share that value and overwrite it.
4. **The console goes to the file inside the app, and only when the flag is present.** The ticket
   forbids a shell script, so nothing can redirect the output from outside. `npm start` keeps its
   console, and the VM's `jiraplane-vm.log` keeps working. Unlike the Mac's log, this one holds only
   what JavaScript writes. Chromium's own stderr does not reach it. An uncaught main-process error
   still shows only as a dialog (#62's gotcha), and this plan adds no handler for it.
5. **A fake `.env` on the VM proves that polling runs.** The VM holds no real token until #68, and
   with no `.env` the app only prints `Polling disabled`. So Step 6 writes a `.env` with fake values
   and a dead local address, and expects `poll cycle failed:` lines 60 seconds apart. That proves the
   timer runs under the login start and that `.env` is found from there. It does not prove a real
   Jira reply: #68 does. Step 11 deletes the file.
6. **One task, uncommitted.** Nobody needs to clone this before accept, unlike #62. The toggle and
   the log share the flag, so a reviewer would not take one without the other.
7. **No docs in this ticket.** `docs/ONBOARDING.md` and `README.md` belong to #68, which is blocked
   by this ticket. Step 12 leaves #68 the facts it needs as a comment.

The `# Visual rule` variant round does not apply: the Settings row does not change.

## What was checked at planning

Read from Electron `v43.2.0` source, which is the `package-lock.json` version. Step 2 proves these
on the VM before any wiring.

- **Do not wrap `args` in quotes, whatever the docs say.** `docs/api/app.md` says "Take care to wrap
  paths in quotes", but `FormatCommandLineString` (`browser_win.cc:161-182`) runs every arg through
  `AddQuoteForArg` (`shell/common/command_line_util_win.cc:11`). That quotes any arg holding a space
  or a backslash and escapes quotes already there, so a self-quoted path breaks. It strips quotes
  around `path` only.
- **`path` must be quoted for the read.** With no `path`, the lookup parses the bare exe path as a
  command line (`browser_win.cc:197-207`), so a folder with a space cuts it short and
  `executableWillLaunchAtLogin` is false. A quoted `path` parses correctly on read and is stripped
  and re-quoted on write.
- **An unknown `--flag` passes through.** `default_app/main.ts:59-60` skips dash args, and the first
  non-dash arg is the app folder.
- **`init.ts` no longer replaces `console` on Windows** (`lib/browser/init.ts`, only one `win32`
  block, about Squirrel), so `console.*` reaches `process.stdout.write` and
  `process.stderr.write` as in Node.
- **`app.getPath('logs')` is not used.** Its pre-ready default was not traced to a provider, and
  `getPath` throws on a miss, which at module load is fatal. `userData` plus `logs` gives the same
  folder.
- **`poller.js` and `main.js` find `.env`, `state.json`, and `settings.json` from `__dirname`,** so
  the login start's working folder does not matter.
- **The VM, read-only:** Windows 11 Pro on Arm, `AutoAdminLogon` is `1`, no value under `Run`, no
  `.env`, `state.json`, or `settings.json` in the clone, and the `jiraplane-vm` task exists.
- **From memory, not read:** Node's console swallows an exception thrown by `stream.write`, so a
  log write that fails does not stop the app. Also from memory: Windows may delay `Run` entries after
  sign-in, and Startup apps may list the item as `Electron`, the exe's name. Step 8 asks.

## Review Focus

1. **The user's folder holds a space** (`C:\Users\First Last\...`). The value must parse and the
   toggle must read On. Step 2 proves the value and the read. A real launch from such a folder is not
   run.
2. **The user switched the app off in Windows' Startup apps page.** The toggle must read Off, and
   clicking On must turn it back on. Step 2.
3. **The clone was moved or renamed while the toggle was On.** The old value points nowhere, so the
   toggle must read Off, and clicking On must replace the value, not add a second one. Step 2.
4. **The Run-key start has a different working folder and no shell.** The app must still find `.env`.
   Step 7 shows `poll cycle failed:` and no `Polling disabled`.
5. **Windows 11 hides a new tray icon behind the `^` arrow.** A login start with no visible icon looks
   like a failure. Step 8 tells the owner to look there, and #68's comment carries it to the docs.
