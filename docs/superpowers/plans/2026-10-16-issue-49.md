> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement

> lockfile change stays uncommitted in the working tree until the owner accepts (AGENTS.md "One
> ticket = two sessions"). The worktree is already on branch `issue-49`; do not commit. **Task 1
> Step 7 is gate 2.** Stop there.

**Goal:** `npm install` on a clean checkout leaves `git status` clean, because the committed
`package-lock.json` already says what npm would write.

**Architecture:** One regenerated file. `package-lock.json`'s root entry still carries
`"license": "UNLICENSED"` from the scaffold commit (`f916268`); `package.json` has said `MIT`
since #8 (`d63a5e4`) and the lockfile was never regenerated after. npm rewrites the root entry
from `package.json` on every install, so every fresh checkout shows the one-line diff. The fix is
to let npm write it once and commit the result. Nothing else in the lockfile moves (proved in a
scratch directory during planning: the diff is exactly line 10).

**Tech Stack:** npm 11.11.0 / node 24.14.1 (owner's Mac, lockfileVersion 3).

**Spec:** No design spec. The decision record is issue #49's body plus the owner's gate-0
answers (2026-10-16, relayed through `/run-ticket`):

- **Done when:** a fresh `npm install` on a clean checkout leaves `git status` clean, and
  `package-lock.json`'s root `license` reads `MIT`, matching `package.json` and `LICENSE`.
- **ONBOARDING §7's `git checkout package-lock.json` recovery step stays.** A coworker who
  already ran `npm install` has a local MIT edit to the lockfile, and the `git pull` that brings
  this very commit still refuses even though the edit matches upstream (HISTORY, #45 review).
  The step goes dead only after everyone has pulled past this commit; #35's rewrite drops it.

## Global Constraints

- The diff is `package-lock.json` only, and within it one line: line 10,
  `"license": "UNLICENSED"` → `"license": "MIT"`. `package.json`, `docs/ONBOARDING.md`,
  `README.md`, `STATE.md` are not in the diff.
- `package.json` keeps `"license": "MIT"`. The lockfile is aligned to it, not the other way.
- `lockfileVersion` stays `3`; no dependency version, `resolved`, or `integrity` field changes.
  If `npm install` changes anything beyond line 10, stop and report the extra hunks at gate 2
  instead of accepting them silently (Review Focus 1).
- T3 gotcha: `npm start` is prefixed `env -u ELECTRON_RUN_AS_NODE` and `TEAMS_WEBHOOK_URL=`
  (no real DM from a test flight).
- One running app instance at a time; quit what you start. Subagents never launch the app.

## Decisions the owner may want to overturn

1. **Plain `npm install`, not `npm install --package-lock-only`.** The ticket's reproduction is
   the command coworkers run; using it makes the build's evidence the same event as the bug. The
   side effect (`node_modules/` populated in the worktree) is gitignored and is needed for the
   full check anyway.
2. **The "fresh checkout" proof is a scratch-directory run, not a second clone.** The fix is
   uncommitted at gate 2, so no clone can contain it yet. Step 5 copies the two manifests to a
   temp dir, runs `npm install --package-lock-only`, and diffs: no output means npm has nothing
   left to rewrite. The literal fresh-clone check happens after accept, when the owner's next
   worktree stops showing the diff.
