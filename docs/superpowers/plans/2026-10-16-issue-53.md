# Login installer fetches the Electron binary — Implementation Plan (jiraPlane #53)

**Goal:** `scripts/install-login-launch.sh` run on a clone that has done `npm install` and
nothing else fetches the Electron binary itself instead of printing a hint that cannot fix it.

**Architecture:** One `if` block changes in the installer. Electron 43's npm package has no
postinstall; `node_modules/electron/install.js` downloads the binary and exits 0 at once when it
is already there (its `isInstalled()` check). The installer keeps its binary check, but when the
binary is missing and `install.js` is present it runs that script (the same call `updater.js`
makes after `npm install`, #48) and carries on. Only when `node_modules/electron` itself is
missing does the old "run 'npm install' first" hint remain, because then it is true.

**Tech Stack:** POSIX `sh` (`set -e`), node 24.14.1 / npm 11.11.0, electron 43.2.0.

**Spec:** No design spec. The decision record is issue #53's body:

- **Done when:** on a fresh clone with `npm install` only, the login installer either fetches
  the binary or names the command that does; the normal ONBOARDING order (step 5 `npm start`
  before step 6 installer) still works unchanged.
- **Constraint:** no new dependency.

## Global Constraints

- The diff is `scripts/install-login-launch.sh` only. `docs/ONBOARDING.md`, `README.md`,
  `docs/usage.md`, `updater.js`, `main.js`, `STATE.md` are not in the diff (ONBOARDING step 6
  says nothing about the binary and still needs nothing).
- No new dependency: the fetch is `node node_modules/electron/install.js`, already shipped
  inside the electron package.
- `set -e` stays: a failed download exits the installer non-zero before any plist is written.
- `--write-only` behaviour (#29) unchanged: the plist is written, launchctl untouched.
- **Never run the installer against the real `$HOME` from this worktree.** The plist embeds
  `$REPO`; a full run would replace the owner's login job with one pointing at the worktree.
  Every installer run in this plan sets `HOME` to a temp dir and passes `--write-only`.
- T3 gotcha: `npm start` is prefixed `env -u ELECTRON_RUN_AS_NODE` and `TEAMS_WEBHOOK_URL=`.
- One running app instance at a time; quit what you start. Subagents never launch the app.

## Decisions the owner may want to overturn

1. **Fetch, not hint.** The ticket allows either. Fetching makes the installer self-sufficient
   and matches what `updater.js` already does after `npm install`; a hint would send the
   coworker to a second command they have never seen. Cost: the installer may now download
   ~100 MB on the no-`npm-start` path, with install.js's own progress output.
2. **`node` from PATH, not an absolute path.** The fetch branch only runs from a coworker's
   terminal (where `node` is on PATH). When `main.js` spawns the installer from the settings
   toggle, the app is already running on the binary, so the check passes and the branch never
   runs. `updater.js`'s `resolveBin` dance is for launchd's bare PATH; this script does not
   need it. If `node` is missing, `set -e` ends the script on the shell's own `node: not found`.

## Login installer fetches the Electron binary — #53 (2026-10-16) — ACCEPTED & CLOSED; commit <hash>
