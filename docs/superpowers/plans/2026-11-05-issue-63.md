# Flight interactions on Windows (#63) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this
> plan. Steps use checkbox (`- [ ]`) syntax for tracking. **One task, so any fix stays uncommitted
> in the working tree.** Three stops: Step 2, Step 4, and Final Step 3 (gate 2). Run every launch and
> stop yourself. Do not hand one to a sub-subagent.

**Goal:** Prove every flight interaction on Windows, and fix only what fails, with Mac behavior
unchanged.

**Architecture:** The ticket says this "may need little or no code", and reading Electron's Windows
source found nothing that must fail. So the plan is a flight checklist with a fix loop, not a set of
planned edits. The owner flies each box in the VM. A failed box gets the smallest fix, and only that
box and click-through fly again.

**Tech Stack:** Electron 43.2.0, Parallels Desktop 27.1.0 (`prlctl`), the VM commands in
`docs/windows-vm.md`.

**Spec:** GitHub issue #63 (`gh issue view 63`). Decisions and fog: parent #60. No design spec.

## Data flow

No data-flow change: the checklist adds no read or write, and `settings.json` and the Jira variables
are read as they are today, with test values for the run.

## Decisions to check at gate 1

1. **No code up front.** Nothing is edited until a box fails in the VM. The alternative is to add
   Windows guards now, but `main.js` needs none by reading (see "What was checked"), and an unneeded
   guard is a line to maintain with no proof it does anything.
2. **Keep the fonts as they are.** The stacks already fall through to Windows fonts. The cargo tag
   gets Comic Sans MS (`comic.ttf` is on the VM). The skywriter text gets Arial, because Arial Rounded
   MT Bold is not on the VM, `-apple-system` matches nothing, and Electron's `sansSerif` default is
   Arial (`electron.d.ts:21282-21285`). Flights 1 and 4 show the result. If the owner wants a
   different face, add one named Windows font after the Mac names, for example `'Segoe UI'` before
   `sans-serif` at `plane.html:177`. A Mac always matches its first font, so the Mac does not change.
   The variant round does not apply: #60 says "Same design, no 3-variant round".
3. **Two displays need the Mac's external monitor plugged in.** At planning the Mac listed only its
   built-in display, and the VM has one display. The only setting found is
   `--fullscreen-use-all-displays` (`man prlctl`): the VM takes over all connected Mac displays in
   full screen. That means no second display in a VM window. The alternative is a virtual-display app
   on the Mac, which is a new tool.
4. **Fake Jira values so the tag can be clicked.** A test flight carries no URL, and with no config
   main derives none (`main.js:220-221`), so `clickable` is false (`plane.html:491`) and a click does
   nothing. Neither the VM nor this worktree has a `.env`. The flights pass
   `JIRA_BASE_URL=https://example.invalid` and three `fake` values as start arguments. The ticket
   then opens `https://example.invalid/browse/PROJ-142`. That name can never resolve, so no fake token
   leaves the machine, the browser shows an error page, and the address bar is the proof. Polling logs
   `poll cycle failed` each minute, which is expected. The alternative is a `.env` on the VM, which
   #61 and #62 keep off it until #68.
5. **Mixed scaling gets one try, and a failure does not get fixed here.** The box lets it be checked
   or written down, and the coworker's displays are unknown. So Step 5 tries it once and records the
   result on #60. If a flight breaks at mixed scale, that becomes a new issue, and the owner decides
   whether the coworker needs it first. Fixing it here could grow without limit for a setup nobody
   has confirmed.
6. **"An app in full screen" means Edge in F11.** From memory, an always-on-top window does not draw
   above a game in exclusive full screen, and code cannot change that. This plan does not test it.
7. **The owner flies each box, with no scripted mouse.** A script could press the mouse from a
   scheduled task on the VM's desktop, but it would have to chase a moving plane. These are also feel
   checks, which AGENTS.md gives to the owner.

## What was checked at planning

- **Electron 43.2.0 source, `shell/browser/`:**
  - `setIgnoreMouseEvents` on Windows sets `WS_EX_TRANSPARENT`, and `forward` installs a `WH_MOUSE_LL`
    hook that posts `WM_MOUSEMOVE` to each window whose client area holds the cursor
    (`native_window_views.cc:1375`, `native_window_views_win.cc:661-756`).
  - `'screen-saver'` is not in the set of levels placed behind the taskbar
    (`native_window_views.cc:1174-1196`), so the overlay stays above it.
  - `enableLargerThanScreen` only sets a size limit on Windows (`:264`).
  - `acceptFirstMouse` does not appear in `native_window_views.cc`.
- **Not run on Windows yet:** the gated start. #62 ran `gated=false`.
- **The VM:** Windows 11 Pro ARM64, version 10.0.26300, one display at 3024x1822, `AppliedDPI` 192
  (200%). By calculation that gives a 1512-wide display and a flight of about 12 s. Edge is the https
  default. No `electron`, no `.env`, no `settings.json`. The clone is at `ab385dd` plus synced files.
- **`scp` to the VM works,** proved with a probe file that was then removed. `settings.json` is
  gitignored, so the sync does not touch it, and `main.js:34-38` reads it once at start.
- **`poller.js`** writes state only after its first fetches succeed, so `state.json` should stay
  absent with fake values. Step 6 removes it anyway.
- **Not a defect:** on Windows the CSS `pointer` cursor may show on the tag (`plane.html:517`). The
  Mac never renders it (#9). Report what the owner sees and leave it.

## Review Focus

1. **Forwarded moves after another app takes focus.** The owner clicks into Notepad first, then
   hovers the plane. The plane must still lift. Flight 1 runs in that order on purpose.
2. **The 24 px margin around the plane (`HIT_PAD`).** The margin is transparent. On Windows a press
   on transparent pixels may fall through to the app below, even while the window is armed. Expected:
   a press just beside the plane grabs it and Notepad gets nothing. Flight 2 asks this. If it fails,
   report it. Do not change `HIT_PAD`, which is a feel value.
3. **The browser takes the foreground in mid-flight.** After the tag click, Edge opens under a flight
   still in the air. The plane must stay above Edge and stay click-through. Flight 1 asks this.
4. **The first gated start on Windows.** With two displays the start waits for the AeroSpace step,
   which here ends at ENOENT. The flight must start, with `gated=true` in the log and no lag near the
   2200 ms backstop. Flights 5 and 6 ask this.
5. **A drag that crosses the seam.** The press belongs to one overlay and the release may land on the
   other. The plane must follow the cursor across and resume on release. The second window also gets
   forwarded moves during the drag, and that has not been run. Flight 5 asks this.

### Task 1: Fly every box in the VM and fix what fails

**Files (only if a box fails, by the fix rule):**
- Modify: `plane.html`, `main.js`

**Interfaces:** none. Later tickets rely on nothing new from this one.

The start line, called "the flight line" below:

```bash
ssh windows-vm 'powershell -NoProfile -ExecutionPolicy Bypass -File jiraPlane\scripts\windows-vm-start.ps1 TEST_FLIGHT=1 TEAMS_WEBHOOK_URL= JIRA_BASE_URL=https://example.invalid JIRA_USERNAME=fake JIRA_USER_KEY=fake JIRA_PAT=fake'
```

To change a setting, write this JSON to a file in your scratchpad, then `scp -q` it to
`windows-vm:jiraPlane/settings.json` before the flight line. Join all three with `&&` so the owner
gets one line:

```text
{"bannerStyle":"cargo","flyOn":"all"}
```

The other values are `skywriter` and `main`.

- [ ] **Step 1: Sync and fly once alone**

Run the sync line from `docs/windows-vm.md`, the flight line, and after about 20 seconds
`ssh windows-vm "type jiraplane-vm.log"`. Expected:

- `<iso> flight: assigned PROJ-142 flyOn=all gated=false displays=[...] rows=[... durMs=N]`
- `poll cycle failed: ...`, and `Polling disabled` does not appear. Polling running is the proof that
  the fake values make a URL.
- no line holding `TypeError`, `Uncaught`, or `UnhandledPromiseRejection`.

If the Parallels window is on the Mac's screen, take a `screencapture -x` during the flight and read
the tag text. Stop the app with the stop line from `docs/windows-vm.md`.

- [ ] **Step 2: Stop 1, the owner flies one display**

End your turn. Hand the owner each flight's line in its own `bash` fence, with these questions. A
flight takes about 12 s, so a late check only needs the line run again. Before Flight 1, the owner
opens Notepad on the VM, maximizes it, and types a few words.

- **Flight 1 (cargo).** Done when 1, 2, 4, and 6. In this order: click in Notepad's text away from
  the plane and tag. Did the caret move, and can you still type? Hover the plane, then the tag: did
  each lift? Could you read the tag text? Click the tag: did Edge open
  `https://example.invalid/browse/PROJ-142`, with an error page expected? Did the plane stay above
  Edge, and could you still click through to Edge away from the plane? Did a box of any color show
  around the plane?
- **Flight 2 (cargo).** Done when 3. Grab the plane, drag it, and release. Did it resume from where
  you dropped it? Press once just beside the plane, not on it: did it grab, or did Notepad get the
  click? Keep going until you have grabbed it three times. Did the third release send it out fast?
  Did the plane stop lifting after that?
- **Flight 3 (cargo).** Done when 6. Press F11 in Edge first. Did the plane fly above it? Press F11
  again after.
- **Flight 4 (`skywriter`).** Done when 4. Could you read the text? Drag does not apply: skywriter
  flights are not draggable by design (#11).

- [ ] **Step 3: Fix what failed**

Apply the fix rule to each failed box. If nothing failed, say so and write no code. Then go on.

- [ ] **Step 4: Stop 2, the owner flies two displays**

Run `prlctl set "Windows 11" --fullscreen-use-all-displays on`. If it refuses while the VM runs, tell
the owner to set it in the VM's configuration, under Options, Full Screen (the path is from memory).
End your turn. Ask the owner to plug in the external monitor, put the VM in full screen, and open
Settings, System, Display on the VM. If the two scales differ, set them the same for now.

- **Flight 5 (`all`).** Done when 5. Did one plane cross both displays with no jump at the seam? Grab
  it and drag it across the seam, then release. Did it follow the cursor and resume?
- **Flight 6 (`main`).** Done when 5. Did the plane fly on the main display only, with nothing on the
  other?

After each flight, read the log. Expected: `flyOn=all gated=true displays=[<a> + <b>]` with two
entries and one marked `primary`, then `flyOn=main gated=true displays=[<a> primary]`.

If the plug-in or full screen does not produce two displays in the log, do not work around it. Report
what the log shows, and let the owner decide.

- [ ] **Step 5: One try at mixed scaling**

Ask the owner to set the two displays to different scales in the same Settings page, if they are not
already. If Parallels forces the scale back, run
`prlctl set "Windows 11" --native-scaling-in-guest on` and try once more. This option is from
`man prlctl`, and whether it needs a VM restart is unknown. If that fails too, stop trying.

If it took, run **Flight 7 (`all`)**. Did the plane cross with no jump? Did a drag follow the cursor
on both displays? Then record the result, in either case, on the parent, where the fog and the
coworker's acceptance live:

```bash
gh issue comment 60 --body "Mixed display scaling (#63): <result in the VM, or: not checked in the VM>. Check on the coworker's PC if their displays differ in scale: fly a test flight with Fly on set to all, and drag the plane across the seam. Expected: no jump at the seam, and the plane stays under the cursor."
```

If Flight 7 broke, also run `gh issue create` with what was seen, and name it in the gate 2 report.
Do not fix it here (Decision 5).

- [ ] **Step 6: Put the VM back**

Ask the owner to reset the scales, leave full screen, and unplug the monitor if they want. Then run
`prlctl set "Windows 11" --fullscreen-use-all-displays off` and, if you changed it,
`--native-scaling-in-guest off`. Stop the app. Delete `settings.json` and `state.json` from the VM's
`jiraPlane` folder. Confirm with `prlctl list -i "Windows 11"` that the settings are back, and over
SSH that neither file exists and no `electron` runs.
