# Display-set logging and the mid-flight display-change decision — Implementation Plan

> **For agentic workers:** this is a **single-task** plan for issue #22. Per `AGENTS.md`, a
> single-task plan **stays uncommitted in the working tree**: no ticket branch, no commits. Build
> it, run the verification below, report what you actually saw, and stop for the owner's gate 2.

**Goal:** Each flight logs the display set it was computed from. Display add, remove and bounds
changes are logged too, with a flag when a flight is in the air. The flight itself does not
react to display changes. That is the decision below (Done-when #1).

**Architecture:** `createFlight` in `main.js` already takes one display snapshot per flight. This
plan adds one log line to it, after the rows are computed. `app.whenReady` gets three `screen`
event handlers that only log. No overlay is rebuilt, moved or destroyed when the display set
changes. `plane.html` does not change.

**Tech Stack:** `main.js` only. Electron `screen` events. No new dependency.

**Spec:** GitHub issue #22 (`gh issue view 22 --repo godfreyponce/jiraPlane --json body,comments`;
the plain `--comments` form printed nothing in the planning session). No comments on the issue.

## Global Constraints

Copied from issue #22. Every step below inherits these.

- Don't rebuild overlays mid-flight unless the decision explicitly calls for it. The #11/#15 drag
  sim holds per-window state, and a rebuild would drop it.
- No polling of the display list. Use the `screen` module's events.
- Single-display setups unaffected.
- One running app instance at a time. Subagents never launch the app. Stop what you start.

## Decisions the owner may want to overturn

1. **Behavior (Done-when #1): a flight keeps the display set it was created with.** Nothing in
   the flight reacts to a display being added, removed or resized. The ticket allows "do nothing,
   it's fine", and this plan picks that, plus logging:
   - A display that **wakes mid-flight** gets no plane for the rest of that flight. On the owner's
     desk that is at most ~12 s (#17 made every flight ~12.0 s; the ticket's "23 s" is from before
     #17). The next flight includes the display.
   - A flight **created while a display sleeps** flies the awake displays only. This is the
     2026-08-06 observation (`minX=0 maxX=1512 durMs=12034`), and the ticket calls it probably
     correct.
   - A flight **created mid-wake**, before enumeration settles, flies whatever
     `getAllDisplays()` returned at that moment. No settle delay: nobody has measured how long
     enumeration takes to settle, so any delay would be a guessed number. The gate 2 run
     (Step 4, D) records that time from the log. It is the receipt a later debounce ticket needs.
   - A display **removed mid-flight**: its overlay is left alone. What macOS does with that window
     has not been observed. It can hide it, or move it onto a remaining display, where it would
     draw a second plane. Gate 2 Step 4, B observes it. If a second plane appears, that is a new
     issue (fix: destroy only that display's overlay on `display-removed`; the other windows keep
     their drag state). It is not added to this build.
   - Why: a rebuild drops #11/#15 drag state (Global Constraint). The flight is short. The ticket
     has low confidence that this has bitten anyone. The log makes every case above visible
     afterwards.
2. **Log shape.** The new lines start with an ISO timestamp. No existing log line has one. But the
   mid-wake case is only visible as "flight line N ms after a `display: added` line", and the
   order of lines alone can't show N. `display-metrics-changed` is logged only when
   `changedMetrics` includes `'bounds'`: a flight reads only `d.bounds`, and `workArea` changes
   when the Dock or menu bar changes, which would only add noise.
3. **#19 is not a blocker.** The ticket says it "depends on #19" (the login instance has no
   logs), but the body does not start with `Blocked by #19`. The logging works now in any dev
   `npm start`. It becomes visible in the always-on instance when #19 lands. #19 is open and not
   labeled.
4. **No `design-directions/` variants.** Nothing visual changes.

## Review Focus

1. **Display removed mid-flight.** macOS may move the orphaned overlay onto a remaining display,
   where it draws a second plane, or the plane in the wrong place. Expected: no second plane.
   Test: Step 4, B (owner). If it happens: open a new issue and report it at gate 2. Do not fix
   it in this build.
2. **Display added mid-flight on a desk where it becomes the primary.** The global origin moves,
   so the running overlays' `minX/maxX/flyY` go stale, and the plane may leave the screen for the
   rest of the flight. This can't happen on the owner's desk. The log shows it as `display:
   bounds ... mid-flight` on the display that stayed awake. Not exercised. Named here so a coworker
   report can be matched to it.
3. **Flight created inside the wake churn.** Expected: the flight line shows a partial or odd set,
   and a `display:` line a few ms before it explains it. Hard to trigger on purpose. Step 4, D
   measures how long the churn lasts.
4. **Display removed during the #21 gated wait** (the ≤2.2 s before `flight-start`). The removed
   overlay's AeroSpace release may exhaust its retries. Expected: the 2200ms backstop starts the
   flight anyway, with no hang. Exercised only if Step 4, B's power-off lands in that window.
   Not required.
5. **Dock / menu-bar changes.** These fire `display-metrics-changed` with `workArea` only.
   Expected: no `display:` line. Test: Step 4, F (owner presses ⌘⌥D twice).

- [ ] **Step 1: Add the helper**

Insert just before the `// Rows engine (#28)` comment (`main.js:166`):

```js
// Log form of a display (#22): id, size and global origin, enough to rebuild
// a flight's rows from the log alone.
function describeDisplay(d) {
  return `${d.id} ${d.bounds.width}x${d.bounds.height}@${d.bounds.x},${d.bounds.y}`;
}
```

- [ ] **Step 2: Log the flight's display set**

Insert right after the `rows` map closes (`main.js:221`, the `});` after `return { displays: rowDisplays, ... }`):

```js
  // #22: the display set this flight was computed from, so a wrong-looking
  // flight can be explained from the log instead of re-investigated.
  console.log(`${new Date(createdAt).toISOString()} flight: ${event.type} ${event.issueKey || '-'} ` +
    `flyOn=${flyOn} gated=${gated} ` +
    `displays=[${displays.map((d) => describeDisplay(d) + (d.id === primary.id ? ' primary' : '')).join(' + ')}] ` +
    `rows=[${rows.map((r) => `minX=${r.minX} maxX=${r.maxX} flyY=${r.flyY} durMs=${r.durMs}`).join(' | ')}]`);
```

- [ ] **Step 3: Log display changes**

Inside `app.whenReady().then(() => { ... })`, insert after `tray.setContextMenu(buildMenu());` and
before `startPolling();`:

```js
  // Display changes (#22): a flight keeps the display set it was created
  // with. Rebuilding overlays mid-flight would drop the #11/#15 drag state,
  // and a display that wakes mid-flight is in the next flight. Logged only.
  const logDisplay = (what, d) => console.log(`${new Date().toISOString()} display: ${what} ` +
    `${describeDisplay(d)}${activeFlight ? ' mid-flight' : ''}`);
  screen.on('display-added', (e, d) => logDisplay('added', d));
  screen.on('display-removed', (e, d) => logDisplay('removed', d));
  // A flight reads only bounds; workArea changes with the Dock and menu bar.
  screen.on('display-metrics-changed', (e, d, changed) => {
    if (changed.includes('bounds')) logDisplay('bounds', d);
  });
```
